## 一、Agent 与模型基础（01—06）

<a id="q01"></a>

### Q01：什么是 Agent？知行与固定工作流的边界在哪里？

- **口述答案**：Agent 是在目标、上下文和权限约束内，由模型决定下一步工具或回答的执行系统。知行的工具选择有模型自主性，但权限、预算、持久化和终止条件由代码控制；学习效果试验则采用明确状态机。产品不需要把每一步都交给模型决定。
- **分析路径**：先判断任务路径是否可预先枚举；再识别需要推理的分支；最后把不可违反的不变量放到执行器。Anthropic 也将预定义编排与模型动态决策区分开。[官方说明](https://www.anthropic.com/engineering/building-effective-agents)
- **Trade-off**：动态决策提高适应性，也增加不可预测性和验证成本；固定流程更可测，但难覆盖开放任务。知行使用混合方案。
- **项目依据**：[AgentService](../../src/agent-service.ts)、[assistant-runtime](../../src/assistant-runtime.ts)、[效果试验状态](../../src/learning-outcomes.ts)、[Agent 循环测试](../../tests/agent-loop.test.ts)。
- **追问 / 易错点**：模型输出一个计划就算 Agent 吗？不够，还应说明工具执行、反馈、退出和失败处理。不要把循环次数多当成自主性强。

<a id="q02"></a>

### Q02：Transformer 和自回归推理与 Agent 延迟有什么关系？

- **口述答案**：注意力机制根据上下文构造 token 表示；常见自回归生成根据已有内容逐步预测后续 token。应用侧一次调用的输入长度、输出长度、思考量和调用次数都会影响体验。知行负责调用和执行控制，没有训练 Transformer 或实现推理引擎。
- **分析路径**：先区分模型计算与网络/进程时间，再区分处理输入与逐步生成。KV cache 可复用已有注意力键值计算，但它不等于应用的对话记忆，也不自动跨用户共享。[Transformer 原论文](https://arxiv.org/abs/1706.03762)、[生成与缓存参数](https://huggingface.co/docs/transformers/main/en/main_classes/text_generation)
- **Trade-off**：减少输入可节约计算，却可能丢失任务条件；压短输出可降低等待，却可能破坏解释。应保留必要信息并实测。
- **项目依据**：[上下文窗口](../../src/context-window.ts)、[阶段耗时](../../src/model-telemetry.ts)、[上下文预算测试](../../tests/agent-context-budget.test.ts)。
- **追问 / 易错点**：不能依据客户端一个总耗时反推 GPU 利用率或模型内部 prefill 时间，客户端没有这些测量。

<a id="q03"></a>

### Q03：上下文窗口、输出上限、字符上限、计费 token 是一回事吗？

- **口述答案**：不是。上下文窗口约束模型能处理的输入与生成空间；输出上限约束该请求允许生成多少 token；字符上限是应用保护边界；实际用量由服务商或官方运行时报告。知行的字符估算只用于调度，不能当账单。
- **分析路径**：核实协议对输入、推理、正文的定义；为输出预留空间；计入工具定义、完整工具轮次、图片和当前输入；记录估算与实际报告的差异。
- **Trade-off**：保守估算会少利用窗口，但减少超限失败；激进估算可能省一次摘要，却增加重试与状态恢复成本。
- **项目依据**：[estimateTokens 与 modelContextWindow](../../src/context-window.ts)、[ModelCapabilities](../../src/model-capabilities.ts)、[图片预算](../../src/image-input.ts)、[预算测试](../../tests/agent-context-budget.test.ts)。
- **追问 / 易错点**：本地 48,000 上下文策略不能说成所有底层模型的官方最大窗口。原生 CLI 也不能用字符截断冒充硬 token 限额。

<a id="q04"></a>

### Q04：temperature、top-p 和思考档位分别控制什么？

- **口述答案**：temperature 改变采样分布的集中程度，top-p 限定候选概率质量；思考档位是具体模型协议对推理投入的控制。它们不是同一旋钮，也不能保证低温输出正确或跨服务商完全确定。[生成参数定义](https://huggingface.co/docs/transformers/main/en/main_classes/text_generation)
- **分析路径**：先确认适配器实际支持哪些参数，再看发送出去的请求。知行向业务暴露 quick、balanced、deep，由适配器映射，不声称这些名字对应相同算力。
- **Trade-off**：任务需要可靠结构时可减少采样波动；需要探索时可允许多样性，但必须独立校验。模型不支持的参数应拒绝或不暴露。
- **项目依据**：[ReasoningProfile](../../src/model.ts)、[Chat Completions 适配](../../src/chat-completions-client.ts)、[成员资源策略](../../src/team-resource-policy.ts)、[推理协议测试](../../tests/provider-reasoning.test.ts)。
- **追问 / 易错点**：项目没有一个对所有提供商通用、语义完全相同的 temperature 调优器。不要把接口字段存在等同于服务商支持。

<a id="q05"></a>

### Q05：模型“思考完却没有答案”是否说明账户没钱？

- **口述答案**：不能直接判断。先区分 HTTP/认证失败、超时、输出截断和预算耗尽。此前异模型团队中，推理与正文共用输出额度，成员可能用尽额度却没形成完整报告；这是生成资源问题，与余额不足是不同故障。
- **分析路径**：看结束原因、推理/正文用量、实际提交档位、单次上限和剩余总预算，再重现固定题。不能仅凭 UI 没答案猜测原因。
- **Trade-off**：增加额度提升完成机会，但增加时延与费用；降低自动思考档位可能更快，也可能增加推理错误，需要审查补偿。显式用户设置优先。
- **项目依据**：[预算策略](../../src/team-resource-policy.ts)、[策略测试](../../tests/team-resource-policy.test.ts)、[历史预算实验](../evidence/team-resource-budget-20260911.md)。
- **追问 / 易错点**：4096/8192/16384 是项目的调度建议，不是厂商规定的最低正确答案预算。

<a id="q06"></a>

### Q06：改 Prompt、做 RAG、微调和换模型，如何选择？

- **口述答案**：先分类失败。输出要求不清先修提示与契约；缺少外部事实先改检索；执行失败先改工具和状态机；稳定的行为分布问题才考虑用数据做微调。换模型要用冻结评测判断，不以品牌替代诊断。
- **分析路径**：收集错误样本，固定基线，每次改变一个主要因素，并记录成本与回归。RAG 原始工作将外部检索与生成结合，但检索成功仍不保证回答忠实。[原始论文](https://arxiv.org/abs/2005.11401)
- **Trade-off**：Prompt 迭代快；RAG 易更新知识但增加检索链路；微调需要训练数据、部署和评测成本。知行当前没有微调流水线。
- **项目依据**：[教学提示](../../src/teaching-prompts.ts)、[资料检索](../../src/library.ts)、[质量评测](../../src/quality-evaluation.ts)、[检索测试](../../tests/retrieval-quality.test.ts)。
- **追问 / 易错点**：RAG 不能“彻底消除幻觉”；微调也不应当作实时知识库。

## 二、接入与可扩展架构（07—12）

<a id="q07"></a>

### Q07：为什么同时需要 ModelClient 和 AgentExecutor？

- **口述答案**：ModelClient 返回逐轮模型事件，知行负责工具执行和续轮；AgentExecutor 返回外部 Agent 的完整任务结果。两者合为 AgentBackend，共享业务内核，但保留执行责任差异，避免外部工具已执行后被知行重复执行。
- **分析路径**：从“谁掌握工具循环”划分接口，而不是从“是不是 HTTP”划分。再明确 prepare、取消、上下文、输出和用量契约。
- **Trade-off**：一个万能 stream 接口表面简单，却容易隐藏工具所有权；双接口增加类型分支，但让安全和预算语义清晰。
- **项目依据**：[AgentBackend](../../src/agent-executor.ts)、[ModelClient](../../src/model.ts)、[统一入口](../../src/agent-service.ts)、[架构边界测试](../../tests/agent-architecture-boundary.test.ts)。
- **追问 / 易错点**：当前原生运行时只启用受限文本上下文任务，不要把接口可扩展性说成外部 Agent 全工具能力已经开放。

<a id="q08"></a>

### Q08：怎样做到新增第十一家模型时不用修改业务代码？

- **口述答案**：若兼容已支持协议，就新增连接配置，提供地址、模型、能力和密钥引用；若是新协议，则实现 ModelClient；若是新官方 Agent 运行时，则实现 AgentExecutor 或 NativeRuntimeAdapter。厂商目录只是配置模板，不是白名单。
- **分析路径**：将“品牌名”“传输协议”“模型能力”“认证方式”拆开；通过工厂与注册表注入；用目录外合成厂商验证扩展路径。
- **Trade-off**：配置化覆盖常见差异；复杂认证和协议差异需要代码。把所有差异做成任意脚本配置会牺牲审查与安全边界。
- **项目依据**：[接入架构](../provider-architecture.md)、[连接配置](../../src/api-connection-config.ts)、[协议测试](../../tests/provider-protocols.test.ts)、[原生扩展测试](../../tests/native-extensibility.test.ts)。
- **追问 / 易错点**：通用架构不是任意网站订阅都自动变成 API；新认证方式仍需官方依据和独立验收。

<a id="q09"></a>

### Q09：为什么不能仅根据模型名称判断图片、工具和窗口能力？

- **口述答案**：名称可能映射到不同版本、代理或套餐。知行把能力显式放入连接与适配器，在发请求前检查图片、工具续轮和预算。能力声明是受控配置，仍需连接级验证。
- **分析路径**：先确定实际模型身份，再检查所需能力，最后限制在应用政策与服务商能力的交集内。
- **Trade-off**：保守拒绝会减少“试试看”的便利；盲目发送可能丢图片、错处理工具或产生隐藏费用。可通过预检改善体验。
- **项目依据**：[能力模型](../../src/model-capabilities.ts)、[动态连接](../../src/api-connections.ts)、[能力测试](../../tests/model-capabilities.test.ts)、[图片测试](../../tests/image-input.test.ts)。
- **追问 / 易错点**：一个模型支持工具，不代表某个中转服务也正确支持并行工具和续轮。

<a id="q10"></a>

### Q10：订阅账号为何通过官方运行时，而不是复制登录 token？

- **口述答案**：让官方运行时管理其认证生命周期，知行管理任务上下文和受控进程。这样避免把服务商私有登录状态变成应用持久密钥，也不在订阅失败时静默改走付费 API。
- **分析路径**：明确认证所有者、执行所有者和计费通道，再验证官方程序版本、权限隔离、输入输出和终止行为。
- **Trade-off**：官方 CLI 更容易复用既有登录，但有启动成本、版本漂移及事件契约依赖；SDK/App Server 可降低某些生命周期成本，但需单独评估和实现。
- **项目依据**：[原生契约](../../src/native-runtime-contract.ts)、[公共宿主](../../src/native-agent.ts)、[Codex 实现](../../src/native-codex.ts)、[实际验收](../evidence/provider-architecture-20260911.md)。
- **追问 / 易错点**：本项目已经验证 Codex 订阅，Claude 真实订阅和 Gemini 执行器仍属后续扩展；不能说三者都已打通。

<a id="q11"></a>

### Q11：三种 API 协议怎样统一流式回答与工具调用？

- **口述答案**：传输层处理分帧、UTF-8、取消和总量上限；协议解码器维护工具与内容状态，再输出统一 ModelEvent。完整的工具请求才进入执行边界，连接特有的续轮状态保留在调用历史中。
- **分析路径**：分别测试半帧、多帧、工具参数跨片段、重复事件、结束标志、截断和用量缺失；不能把每个 SSE 片段直接作为可执行 JSON。
- **Trade-off**：统一事件方便业务复用，但不能丢失协议必须回传的状态。保留不透明状态比强行扁平化更安全。
- **项目依据**：[HTTP 帧读取](../../src/provider-http.ts)、[协议编解码](../../src/protocol-codecs.ts)、[协议客户端](../../src/protocol-model-client.ts)、[协议测试](../../tests/provider-protocols.test.ts)。
- **追问 / 易错点**：HTTP 200、流结束和业务完成是不同条件；截断流不能被包装成完整成功。

<a id="q12"></a>

### Q12：为什么任务恢复要冻结模型身份和连接？

- **口述答案**：恢复应延续原任务的执行条件。若配置中的模型、连接、权限范围或预算策略改变，就不能悄悄把后半程交给另一套条件；应阻止不兼容恢复或创建新任务。
- **分析路径**：绑定 provider、model、connection、reasoning 等身份，保存配置与上下文范围摘要，恢复时比较，再加载已经完成的产物。
- **Trade-off**：冻结降低运行中热切换灵活性，但提高可追溯性、实验公平性和故障解释能力。
- **项目依据**：[模型绑定](../../src/agent-model-binding.ts)、[TeamCoordinator.create](../../src/team-coordinator.ts)、[团队隔离测试](../../tests/team-isolation.test.ts)、[任务恢复测试](../../tests/team-task-recovery.test.ts)。
- **追问 / 易错点**：配置里的显示名称没变，不代表底层模型没变；供应商别名升级也是需要记录的外部变量。

## 三、状态、记忆与上下文（13—18）

<a id="q13"></a>

### Q13：知行有哪些不同的“记忆”？

- **口述答案**：至少区分原始对话、当前模型窗口、会话摘要、来源明确的长期记忆、学习画像/实际作答记录，以及执行检查点。它们分别服务于回看、生成、衔接、检索、教学和恢复，不能共用一个不断增长的 Prompt。
- **分析路径**：为每类数据定义来源、范围、生命周期、撤销方式和读取权限；模型总结不能直接升级为用户事实或完成状态。
- **Trade-off**：分层增加数据关联复杂度，但能控制污染、撤销和窗口成本；全量拼接实现简单却难长期维护。
- **项目依据**：[学习上下文](../../src/learning-context.ts)、[会话存储](../../src/agent-session-store.ts)、[会话摘要](../../src/conversation-summary.ts)、[执行存储](../../src/agent-execution-store.ts)。
- **追问 / 易错点**：模型 KV cache、会话摘要、长期记忆是三种不同东西。

<a id="q14"></a>

### Q14：摘要有来源哈希，是否就能证明摘要正确？

- **口述答案**：哈希只证明摘要覆盖的源记录仍然匹配，不证明摘要忠实或语义正确。知行保存覆盖到哪条消息和源哈希，源记录变化后旧摘要不再作为有效覆盖。
- **分析路径**：先校验来源范围，再判断是否需要新的摘要；关键目标、约束和实际执行状态通过结构化数据保留，不依赖摘要独自承担。
- **Trade-off**：摘要降低上下文成本但会遗漏信息；保存原文和来源边界提高可恢复性，却需要额外存储与校验。
- **项目依据**：[summarySourceHash / verifiedSummaryThrough](../../src/conversation-summary.ts)、[摘要覆盖测试](../../tests/summary-coverage.test.ts)、[结构化上下文测试](../../tests/structured-context.test.ts)。
- **追问 / 易错点**：“哈希通过，所以摘要无幻觉”是错误结论。语义忠实需要独立评测。

<a id="q15"></a>

### Q15：长对话超出预算时，为何不能从最早字符直接截断？

- **口述答案**：字符截断可能切断工具调用与结果，丢失用户纠正或破坏协议。知行生成一次性的模型上下文视图，优先移除完整较早工具轮次与可移除消息，保留系统信息、关键边界和当前待执行内容，原始记录不被改写。
- **分析路径**：计算完整请求预算，保留不可拆分结构；仍无法容纳时明确失败，不能把一半工具结果交给模型继续执行。
- **Trade-off**：保留完整轮次可能比按字截断更早触发上限，但避免协议错误与执行重复。
- **项目依据**：[modelContextWindow](../../src/context-window.ts)、[上下文测试](../../tests/agent-context-budget.test.ts)、[恢复边界测试](../../tests/agent-recovery-boundaries.test.ts)。
- **追问 / 易错点**：可见 UI 历史完整，不代表每轮都发送全部历史；应向用户说明遗漏但不得编造被省略事实。

<a id="q16"></a>

### Q16：长期记忆相关性和冲突如何处理？

- **口述答案**：先限制主题和授权，再按问题检索相关记录，并保留来源。知行对相关记忆做有界摘录，也覆盖同义表达；没有相关项时才使用近期回退。用户修正不能被更旧的相反记录覆盖。
- **分析路径**：拆分“是否相关”“是否可信”“是否过时”，用冲突和撤回案例验证，不只检查简单关键词命中。
- **Trade-off**：只取最新记录会漏掉很早的关键事实；只看相关性会引入旧错误。需要来源、时间和用户纠正共同约束。
- **项目依据**：[LearningContextBuilder.snapshot](../../src/learning-context.ts)、[记忆检索](../../src/database.ts)、[记忆质量测试](../../tests/memory-recall-quality.test.ts)。
- **追问 / 易错点**：项目的记忆选择是有界检索策略，不是已经实现通用事实冲突推理或知识图谱。

<a id="q17"></a>

### Q17：如何从架构上保证桌面与 CLI 的记忆、权限策略相同？

- **口述答案**：两端作为传输和展示层，进入同一 AgentService 与 LearningApplication；上下文构建、授权和状态迁移留在共享模块。但共享核心不等于入口已完全一致：本轮发现 CLI 超过 8,000 字符提前拒绝，而共享发送契约采用 20,000 字符上限，这是尚待修复的宿主边界差异。
- **分析路径**：检查是否存在某端绕过共享入口、私自拼 Prompt 或缓存旧授权；撤权后下一轮必须重新构建上下文。
- **Trade-off**：共享核心提高一致性，但两端 UI 表达可以不同；要求政策相同不意味着终端和桌面代码完全相同。
- **项目依据**：[AgentService.invoke](../../src/agent-service.ts)、[CLI 提前校验](../../src/cli.ts)、[共享输入限额](../../src/input-limits.ts)、[统一政策测试](../../tests/unified-agent-policy.test.ts)。
- **追问 / 易错点**：仅复用同一个模型类无法保证记忆一致，还要共用读取、授权、写回和恢复路径。应补测 8,001—20,000 字符入口；现有统一政策测试不能证明此前没有遗漏。

<a id="q18"></a>

### Q18：长会话文件如何避免每次保存都越来越慢？

- **口述答案**：知行将较早消息按内容哈希分段保存，主文件保留段索引和尾部，读取校验段内容与会话身份；写入按会话串行并使用原子替换。它优化本地存储，不意味着拥有无限对话容量。
- **分析路径**：测量消息数增长下的序列化、磁盘写入、索引和 UI 渲染，再针对主导成本优化；同时保留大小上限。
- **Trade-off**：分段减少重复写入，增加段管理和损坏检查；单 JSON 易理解，但长会话重写成本更高。
- **项目依据**：[AgentSessionStore](../../src/agent-session-store.ts)、[分段会话测试](../../tests/segmented-conversation.test.ts)、[会话扩展性测试](../../tests/session-scaling.test.ts)。
- **追问 / 易错点**：当前分段按 250 条消息组织；不要把此策略称为分布式日志存储。

## 四、RAG 与证据（19—24）

<a id="q19"></a>

### Q19：PDF / Markdown 导入时如何选择切块与元数据？

- **口述答案**：切块要保留可定位的页码或锚点，并保存文档、主题和内容版本。知行进行格式、大小、页数及重复检查；扫描 PDF 通过 OCR 流程处理，低置信度不能伪装成可靠原文。
- **分析路径**：先看文档结构与问题分布，再试不同块大小，分别测召回和最终回答。避免把公式、表格的关键条件拆散。
- **Trade-off**：小块定位精确但上下文不足；大块信息完整但噪声与 token 成本更高。结构化切块和重叠参数应由评测驱动。
- **项目依据**：[DocumentLibrary](../../src/library.ts)、[OCR](../../src/ocr.ts)、[导入测试](../../tests/integration.test.ts)、[检索测试](../../tests/retrieval-quality.test.ts)。
- **追问 / 易错点**：项目还没有面向所有 PDF 表格与版面的高精度解析保证；先说明现有限额和扫描件状态。

<a id="q20"></a>

### Q20：知行的 HashEmbedding 是语义向量模型吗？

- **口述答案**：它是确定性的本地哈希特征，不具备训练过的语义理解能力。当前词法检索依赖查询扩展和排序；可选 Ollama 本地嵌入另行建立语义索引。不能因为存了向量就宣传为高质量语义检索。
- **分析路径**：分别测试同义问法、无关词碰撞、多语言和长文档；检查真正使用的检索路径，而非只看类名。
- **Trade-off**：词法方案轻量、离线、可解释，但语义覆盖有限；真实嵌入改善语义匹配，同时增加本地模型依赖、资源消耗和版本管理。
- **项目依据**：[HashEmbeddingModel](../../src/embedding.ts)、[词法排序](../../src/retrieval-query.ts)、[SemanticIndex](../../src/semantic-retrieval.ts)、[检索测试](../../tests/retrieval-quality.test.ts)。
- **追问 / 易错点**：不能说知行已经部署了云端向量数据库或交叉编码器。

<a id="q21"></a>

### Q21：RRF 融合与 reranker 有什么区别？项目用了什么？

- **口述答案**：知行的 fuseEvidence 根据两个结果列表的排名贡献融合并去重，不比较不同检索器原始分数。它不是再训练一个模型判断“问题与文段是否相关”的交叉编码重排器。
- **分析路径**：先提高候选召回，再决定融合和重排；比较 top-k 命中、噪声、延迟和输入成本。现有融合实现可以作为基线。
- **Trade-off**：排名融合简单且不需要分数校准；模型重排可能更精准，但增加推理开销和部署复杂度，收益需用资料集验证。
- **项目依据**：[fuseEvidence](../../src/semantic-retrieval.ts)、[rankEvidence](../../src/retrieval-query.ts)、[检索质量测试](../../tests/retrieval-quality.test.ts)。
- **追问 / 易错点**：把“排序函数”叫作“已部署神经网络 reranker”会被代码追问击穿。

<a id="q22"></a>

### Q22：答案带引用，为什么仍然可能错误？

- **口述答案**：引用可定位只证明片段存在；答案可能误读原文、引用了不支持的数值或忽略条件。知行进一步检查引用来源、精确数值、引号与过强措辞，但明确不宣称这些规则证明语义蕴含。
- **分析路径**：把引用有效性、证据支持度、推导正确性和表达质量分开；无证据时保留不确定或拒绝来源限定回答。
- **Trade-off**：严格证据规则降低错误断言，也可能误伤合理推导；因此需要可解释错误与人工/模型复核，而不是一个“可信”总开关。
- **项目依据**：[inspectEvidenceSupport](../../src/evidence-support.ts)、[answerFromEvidence](../../src/grounded-answer.ts)、[证据测试](../../tests/evidence-support.test.ts)、[引用回答测试](../../tests/grounded-answer.test.ts)。
- **追问 / 易错点**：数值在某个片段中出现，不代表它属于答案所声称的指标或实验。

<a id="q23"></a>

### Q23：如何评估 RAG，才能分清“没找到”与“答错了”？

- **口述答案**：建立带相关片段标注的问题集，先测检索是否覆盖必要证据，再在固定证据下测生成是否忠实，最后测端到端。另设无答案、跨主题、旧版本和注入案例。
- **分析路径**：记录正确片段是否进入候选和最终上下文；若已进入仍答错，优先分析提示、证据冲突和推理；若根本没进入，改切块和检索。
- **Trade-off**：细粒度标注成本高，但比只看最终“像不像对”更能定位改进。自动指标应与人工判定校准。
- **项目依据**：[检索评测用例](../../tests/retrieval-quality.test.ts)、[grounded-answer 测试](../../tests/grounded-answer.test.ts)、[质量评测](../../src/quality-evaluation.ts)。
- **追问 / 易错点**：若引入 recall@k，先定义一题有几个必需片段及分母；不要把返回条数当作召回率。

<a id="q24"></a>

### Q24：资料更新、模型更新后，旧索引和旧验证还能用吗？

- **口述答案**：要匹配内容与模型版本。知行语义索引记录模型身份和内容哈希，实际 Ollama 模型摘要变化会被识别；项目证据也绑定实际内容哈希，代码或测试改变后旧验证不能自动继续有效。
- **分析路径**：为每个派生产物写清依赖：原文、切块、嵌入模型、提示和代码。只复用依赖仍一致的结果。
- **Trade-off**：严格失效增加重建成本；宽松复用速度快，却可能给旧答案套上新证据。
- **项目依据**：[SemanticIndex](../../src/semantic-retrieval.ts)、[source-version](../../src/source-version.ts)、[EvidenceStore](../../src/evidence-store.ts)、[证据应用测试](../../tests/evidence-application.test.ts)。
- **追问 / 易错点**：模型名相同但实际权重摘要改变，也可能需要失效；内容哈希本身不证明内容可靠。

## 五、工具执行与故障恢复（25—30）

<a id="q25"></a>

### Q25：为什么要有统一 ToolHarness？

- **口述答案**：模型只能提出工具调用，ToolHarness 才执行输入校验、主题边界、风险上限、超时和结果限制。把这些规则放在每个 Prompt 或每个工具里容易产生不一致。
- **分析路径**：明确工具定义、运行上下文和结果契约；执行前校验，执行后限制输出；审计只暴露必要诊断信息。
- **Trade-off**：统一边界让扩展更可靠，但工具的业务幂等性与外部副作用仍需工具自身明确声明和实现。
- **项目依据**：[ToolHarness](../../src/tool-harness.ts)、[ToolDispatcher](../../src/tool-dispatcher.ts)、[工具边界测试](../../tests/tool-harness.test.ts)、[工具契约测试](../../tests/tool-spec.test.ts)。
- **追问 / 易错点**：工具名称在白名单中不代表参数合法，更不代表当前任务有写权限。

<a id="q26"></a>

### Q26：JSON Schema 或结构化输出能保证工具调用安全吗？

- **口述答案**：只能保证部分形状约束。合法字符串也可能指向越权路径，合法对象也可能请求不允许的操作；必须继续做业务语义和权限校验。远端 MCP Schema 的复杂度也需要约束。
- **分析路径**：从协议校验到业务校验，再到授权、执行和结果验证分层；禁止以模型自报的 topicId 覆盖运行上下文。
- **Trade-off**：严格 schema 减少歧义，但不能替代执行时检查；宽松 schema 方便模型调用，却增加错误修复成本。
- **项目依据**：[validatedPreview](../../src/tool-harness.ts)、[Schema 隔离 worker](../../src/json-schema-worker.ts)、[Schema 方言测试](../../tests/json-schema-dialects.test.ts)、[路径政策测试](../../tests/path-policy.test.ts)。
- **追问 / 易错点**：JSON 可解析与业务可执行是不同标准；Zod 的字段剥离也不能抹掉原始参数中已经存在的越权意图。

<a id="q27"></a>

### Q27：工具报错应该抛异常、让模型重试，还是直接失败？

- **口述答案**：按类型处理。参数错误返回可修正的结构化信息；权限失败不能靠重试绕过；外部临时错误可以在明确预算内重试；副作用结果未知应进入恢复状态。不要把所有错误都化成一句“重试”。
- **分析路径**：区分输入、业务、基础设施、取消和未知结果；给模型错误代码与字段位置，避免把凭据或原始敏感参数返回到上下文。
- **Trade-off**：详尽诊断便于自修复，也增加泄密和提示注入风险；白名单化错误可减少风险但要求维护错误目录。
- **项目依据**：[toolFailure](../../src/tool-harness.ts)、[公开错误](../../src/agent-errors.ts)、[工具调度测试](../../tests/tool-dispatcher.test.ts)、[MCP 工具测试](../../tests/mcp-tools.test.ts)。
- **追问 / 易错点**：MCP 协议错误与工具执行错误也不同，不能只根据 HTTP 成功判断业务成功。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

<a id="q28"></a>

### Q28：为什么“超时了，再执行一次”会造成严重问题？

- **口述答案**：超时只表示客户端没有拿到确定结果，外部写入可能已经发生。知行对已派发的非幂等写调用保留未知结果，要求核实或明确报告，不自动重放。
- **分析路径**：先持久化执行意图，再派发；把未开始、执行中未知、已确认成功分开；恢复时优先查询外部状态或利用服务端幂等键。
- **Trade-off**：保守恢复降低自动化程度，但避免重复发消息、重复创建资源或重复扣费。服务端幂等支持能改善体验，但不是所有工具都有。
- **项目依据**：[ToolOutcomeUnknown](../../src/tool-harness.ts)、[TaskContinuity](../../src/task-continuity.ts)、[MCP 恢复](../../src/mcp-recovery.ts)、[恢复边界测试](../../tests/agent-recovery-boundaries.test.ts)。
- **追问 / 易错点**：用户说“已经成功”可以记为用户报告，不能标成服务端已核验；本地日志也不能单独提供跨服务 exactly-once 保证。

<a id="q29"></a>

### Q29：取消一个 Agent 任务需要取消哪些东西？

- **口述答案**：包括排队等待、网络读取、模型进程、工具、成员任务、摘要维护和 UI 订阅的相关工作。取消之后不得再启动新副作用；已发生的写入不能因为取消而被抹掉。
- **分析路径**：传播同一取消链，合成父级信号与局部超时，清理监听器和进程，再把状态持久化为 interrupted/cancelled 等真实结果。
- **Trade-off**：强制终止进程响应快，但无法自动回滚外部操作；协作式取消更容易清理，却要防工具不响应。
- **项目依据**：[AgentService.stop 相关逻辑](../../src/agent-service.ts)、[abortable](../../src/abortable.ts)、[原生进程宿主](../../src/native-agent.ts)、[生命周期测试](../../tests/agent-cli-lifecycle.test.ts)。
- **追问 / 易错点**：Promise.race 超时不会自动杀掉底层任务；必须解释被竞争的操作如何真正收到取消信号。

<a id="q30"></a>

### Q30：哪些工具可以并行？怎样防止死循环？

- **口述答案**：只读不必然独立，只有显式声明纯读、幂等且 parallelSafe 的工具才可进入安全并行。LoopGuard 同时限制模型轮数和相同状态下重复工具调用，写入改变资源状态后应重新判断观察是否有效。
- **分析路径**：先确定共享资源和副作用，再安排并行；规范化参数用于重复检测，保留数组顺序，不能只比较字符串键顺序。
- **Trade-off**：更多并行降低墙钟时间，但增加竞争与错误传播；严格限制可能少用并发，却能保持执行语义。
- **项目依据**：[工具并行声明](../../src/tool-harness.ts)、[LoopGuard](../../src/loop-guard.ts)、[并行测试](../../tests/agent-parallel.test.ts)、[循环测试](../../tests/loop-guard.test.ts)。
- **追问 / 易错点**：重复读取在外部状态变化后可能合理；防循环键必须考虑资源状态，而非永久封禁同参数。

## 六、同模型与异模型团队（31—36）

<a id="q31"></a>

### Q31：单 Agent、同模型团队、异模型团队分别适合什么？

- **口述答案**：单 Agent 适合简单或强依赖任务；同模型团队便于在相同能力与协议下分工独立检查；异模型团队可能带来不同能力和错误模式，但增加协调、延迟与能力对齐成本。默认不应假设团队一定更好。
- **分析路径**：先看可分解性和独立核验价值，再看单模型基线是否已经足够；同模型多次调用也不等于独立统计样本。
- **Trade-off**：同模型更易控变量但错误相关；异模型潜在多样性更高但并非天然互补。应按任务分层比较真实收益。
- **项目依据**：[团队配置](../../src/team-contracts.ts)、[协调器](../../src/team-coordinator.ts)、[历史对照](../evidence/team-resource-budget-20260911.md)。
- **追问 / 易错点**：知行当前团队是主 Agent 编排的有界只读核查，不是成员任意互聊、递归生成无限子 Agent 的系统。

<a id="q32"></a>

### Q32：为什么团队用 DAG，而不是简单 Promise.all？

- **口述答案**：有的任务依赖前一个结果，有的任务可独立执行。DAG 显式表达依赖，运行时拒绝循环和缺失依赖，并按可执行波次调度；同一成员的任务也不能冲突并行。
- **分析路径**：规划时验证任务 ID、成员覆盖和依赖；派发前先存意图；失败后阻塞依赖任务；保存实际执行 ID 和尝试次数。
- **Trade-off**：DAG 更可追踪，但规划和验证增加开销。只有两个独立短核查时简单并行足够，不必制造复杂依赖。
- **项目依据**：[parseTaskPlan / runTaskGraph](../../src/team-task-graph.ts)、[工作契约](../../src/team-work-contracts.ts)、[图测试](../../tests/team-task-graph.test.ts)。
- **追问 / 易错点**：项目任务图数量和重试有上限；不要把本地波次调度说成已经实现跨机器工作队列。

<a id="q33"></a>

### Q33：团队为什么可能比单 Agent 答得更差？

- **口述答案**：常见原因是错误分工、共享了不完整上下文、成员因预算截断、内部格式污染任务、错误多数票、综合阶段丢条件，以及额外调用引入故障。团队还可能重复同一个模型的偏差。
- **分析路径**：分别检查规划、成员、审查、综合产物，定位最早错误；再做移除某阶段、扩大预算或统一上下文的消融，而非直接宣布模型不够强。
- **Trade-off**：多一层审查能发现部分错误，却也能引入新误判和延迟；应以可验证问题驱动定向复核。
- **项目依据**：[团队质量协议](../../src/team-quality.ts)、[规划范围约束](../../src/team-task-graph.ts)、[历史失败与修复](../evidence/team-resource-budget-20260911.md)、[质量测试](../../tests/team-quality.test.ts)。
- **追问 / 易错点**：历史 H02 最终正确是审查纠正成员错误的结果，不证明所有成员更准确，也不证明降低思考档位提高智力。

<a id="q34"></a>

### Q34：主 Agent 说“大家都同意”，为什么不能判团队验收成功？

- **口述答案**：一致意见可能共同错误。知行按每项任务验收条件建立覆盖关系，审查需要引用具体任务及依据；区分 unresolved、model-reviewed 和 evidence-linked，不能把模型自评提升为工具实证。
- **分析路径**：检查任务是否完成、验收条件是否逐项覆盖、证据 ID 是否属于本次执行且成功、是否仍有不确定项。
- **Trade-off**：细粒度覆盖比一个总分昂贵，但能暴露遗漏和伪造依据；仍然不能把结构覆盖等同于数学证明。
- **项目依据**：[verifyTeam](../../src/team-verification.ts)、[团队证据测试](../../tests/team-verification.test.ts)、[工具证据测试](../../tests/team-tool-evidence.test.ts)。
- **追问 / 易错点**：evidence-linked 表示证据链关联完整，不代表原证据和推导永远正确。

<a id="q35"></a>

### Q35：成员应该共享全部主 Agent 上下文吗？

- **口述答案**：不应默认共享。知行建立受控任务包，显式处理 shareContext；成员报告和原始材料视为数据，不能改变系统指令、授权或最终交付格式。成员保持只读且不能继续委派。
- **分析路径**：按子任务传必要问题、条件、材料及依赖结果；不要复制主 Agent 私有历史和所有资料。审查同样只看规定输入。
- **Trade-off**：最小上下文减少泄露、污染和 token 成本，但可能漏掉重要条件；需要任务包完整性和缺失信息处理。
- **项目依据**：[任务包](../../src/team-task-packet.ts)、[成员调用](../../src/team-coordinator.ts)、[团队隔离测试](../../tests/team-isolation.test.ts)。
- **追问 / 易错点**：仅在 Prompt 里写“你是只读”不够，还必须由权限与工具执行层限制。

<a id="q36"></a>

### Q36：团队部分失败后怎样恢复，才不重复消耗所有成员？

- **口述答案**：保存规划、任务状态、执行 ID、已完成报告、资源预留和模型绑定；重启后运行中的任务标记中断，按明确的可重试条件定向恢复。已有成功报告保留，不能重跑后覆盖旧事实。
- **分析路径**：验证配置和范围未变，再判断目标任务及其依赖能否继续；保留各次 run 记录，给新执行分配新 ID。
- **Trade-off**：定向恢复比全量重跑复杂，但降低费用并保留因果链；若上游条件确实变化，应新建任务而非勉强复用。
- **项目依据**：[团队恢复](../../src/team-coordinator.ts)、[任务重试规则](../../src/team-work-contracts.ts)、[崩溃恢复测试](../../tests/team-crash-recovery.test.ts)、[任务恢复测试](../../tests/team-task-recovery.test.ts)。
- **追问 / 易错点**：恢复不是“模型接着聊”；它还要保证权限、预算和外部效果的一致性。

## 七、预算、性能与可观测性（37—42）

<a id="q37"></a>

### Q37：如何保证并行成员不会同时把预算花超？

- **口述答案**：发送前串行持久化预算预留，为分工、审查和最终回答保留额度；拿到权威用量后结算。用量未知保留预留，存储失败则禁止新请求，而不是继续请求后再补记。
- **分析路径**：检查预留操作是否原子串行、取消是否发生在派发前、重复 usage 是否重复结算、失败是否丢失未知消费。
- **Trade-off**：保守预留降低预算利用率，但避免把网络失败当零成本。原生 CLI 没有硬 token 限额，只能报告观察性质并用时间、字符和次数限制。
- **项目依据**：[TeamBudget](../../src/team-budget.ts)、[预算测试](../../tests/team-budget.test.ts)、[成员策略测试](../../tests/team-resource-policy.test.ts)。
- **追问 / 易错点**：输出 token 总量不等于金额；异模型计费规则不同，金额估算需独立版本化价格表和准确用量。

<a id="q38"></a>

### Q38：如何定位“连接模型很慢”？

- **口述答案**：拆分模型选择、进程启动、认证准备、请求等待、首事件、首正文、生成完成和退出清理。再区分网络路径、模型推理、工具等待和本地渲染，不能只看一个总秒数。
- **分析路径**：用固定最小题复测直接与指定代理路径，记录成功和失败；将进程事件与可见文本分开。原生首次完整消息不能冒充流式首 token。
- **Trade-off**：细分观测有助定位，但只能描述客户端看得到的阶段；过度推断服务端原因会误导优化。
- **项目依据**：[ModelTiming](../../src/model-telemetry.ts)、[延迟测试](../../tests/pi-latency.test.ts)、[三家检查记录](../evidence/provider-architecture-live-20260911.json)。
- **追问 / 易错点**：三家各一次固定题检查的耗时不能用来给模型整体速度排名。

<a id="q39"></a>

### Q39：流式 UI 为什么不能每个 token 都全量刷新会话？

- **口述答案**：频繁全量更新会增加 IPC、序列化和渲染成本。知行发送带序号的消息补丁并在渲染端合并 delta，结束时确保最终文本刷新；订阅者断开不能反过来控制任务是否完成。
- **分析路径**：测每秒事件数、主线程阻塞、累计文本复制与最后一段丢失；处理切会话、旧快照覆盖和取消清理。
- **Trade-off**：批处理减少开销但略增显示延迟；窗口要小且结束时强制 flush。不能为了平滑动画延迟真正停止。
- **项目依据**：[AgentService.patch / emit](../../src/agent-service.ts)、[delta-batcher](../../desktop/renderer/delta-batcher.ts)、[批处理测试](../../tests/stream-batcher.test.ts)。
- **追问 / 易错点**：把整个应用变成高频轮询不等同于可靠恢复；应区分实时事件和断线后的状态读取。

<a id="q40"></a>

### Q40：Prompt cache、应用缓存、语义索引缓存如何区分？

- **口述答案**：模型服务的输入缓存复用计算；应用缓存复用配置或本地查询结果；语义索引缓存复用特定模型与文本的向量。它们的命中条件和隐私边界不同，不能统一叫“记忆命中”。
- **分析路径**：定义缓存键包含什么版本、什么时候失效、是否跨权限范围；授权撤回后的上下文不能继续来自旧缓存。
- **Trade-off**：缓存提高速度，但过粗键会串会话、串模型或泄露已撤权内容。先做有来源的局部缓存，别缓存整个可变 Prompt。
- **项目依据**：[学习上下文逐轮重建](../../src/learning-context.ts)、[语义索引键](../../src/semantic-retrieval.ts)、[缓存用量口径](../../src/model-capabilities.ts)、[统一撤权测试](../../tests/unified-agent-policy.test.ts)。
- **追问 / 易错点**：项目没有通用跨请求答案缓存，不能将供应商 cacheReadTokens 说成知行自己实现的缓存命中率。

<a id="q41"></a>

### Q41：如果增加自动重试，怎样避免雪崩与超时失控？

- **口述答案**：先判断是否可重试与是否可能已有副作用；所有尝试共享总截止时间和预算，采用有上限的退避与并发控制，不能每次重试重新获得完整预算。现有知行有单次超时和预算边界，并非所有协议已具备统一退避重试器。
- **分析路径**：区分限流、认证、永久参数错误、断流和未知结果；测试取消能终止退避等待，恢复不会重复收费性工作。
- **Trade-off**：重试提高短暂故障成功率，也可能放大流量、费用和延迟；低成本只读操作与外部写操作应采用不同政策。
- **项目依据**：[协议超时处理](../../src/protocol-model-client.ts)、[预算并发限制](../../src/team-budget.ts)、[取消工具](../../src/abortable.ts)、[原生运行时测试](../../tests/native-agent.test.ts)。
- **追问 / 易错点**：这一题中的统一退避策略是扩展设计，不要说当前已经部署了服务商级熔断集群。

<a id="q42"></a>

### Q42：如何证明一次性能优化有效？

- **口述答案**：固定任务、模型版本、档位、预算和测量口径，保留冷启动与热运行、成功与失败，报告分位数和资源消耗，并确保质量不下降。单次变快只能作为线索。
- **分析路径**：先建立阶段基线，找到关键路径，再做单因素实验；若同时改代理和思考档位，应如实说明无法把收益唯一归因于一项改动。
- **Trade-off**：严格实验耗时更高，但避免优化错方向；真实调用成本可通过离线协议测试与小规模线上验证组合控制。
- **项目依据**：[耗时测量测试](../../tests/provider-measurement.test.ts)、[历史预算实验](../evidence/team-resource-budget-20260911.md)、[模型审计](../../src/model-audit.ts)。
- **追问 / 易错点**：团队墙钟时间取决于依赖关键路径，并不等于所有成员耗时相加，也不总等于最长成员时间。

## 八、存储、桌面与安全（43—48）

<a id="q43"></a>

### Q43：为什么项目同时有 SQLite 和 JSON，而不是统一一种存储？

- **口述答案**：SQLite 承担结构化学习数据、执行状态和事务；会话 JSON 便于独立保存、迁移与分段。各有职责，但跨两种存储不存在天然全局事务，需要恢复逻辑处理边界。
- **分析路径**：按查询模式、事务要求、迁移和备份设计存储；避免把 UI 文本当执行事实来源。
- **Trade-off**：多存储降低单一模型的复杂度，却增加一致性与备份要求；全部进数据库便于事务，但迁移和长文本组织也要设计。
- **项目依据**：[数据库](../../src/database.ts)、[会话存储](../../src/agent-session-store.ts)、[执行存储](../../src/agent-execution-store.ts)、[存储测试](../../tests/desktop-storage.test.ts)。
- **追问 / 易错点**：SQLite 事务原子性有自身日志与落盘机制，不能推论它也涵盖外部文件或服务。[SQLite 原子提交](https://sqlite.org/atomiccommit.html)

<a id="q44"></a>

### Q44：进程在工具执行中崩溃，如何知道下一步该做什么？

- **口述答案**：依靠持久检查点和事件，而非模型记忆。检查点保存已完成轮次、当前调用、派发阶段和消费；恢复先确认是否有未知外部效果，再决定可重放读取、继续生成或等待核实。
- **分析路径**：在派发前后、写结果前后、最终验证时注入崩溃，检查系统不会重复副作用或错误标完成；并防两个本地进程同时认领同一执行。
- **Trade-off**：更多检查点提高恢复精度，但增加写入次数和状态复杂度；应把不可恢复边界优先覆盖。
- **项目依据**：[AgentExecutionStore](../../src/agent-execution-store.ts)、[连续任务](../../src/task-continuity.ts)、[崩溃测试](../../tests/agent-crash.test.ts)、[检查点测试](../../tests/agent-checkpoint.test.ts)。
- **追问 / 易错点**：项目的本地认领机制不能直接当作分布式租约算法，需要重新处理时钟、网络分区和 fencing。

<a id="q45"></a>

### Q45：备份成功意味着恢复后可以直接继续所有任务吗？

- **口述答案**：不意味着。恢复需验证文件、数据库与引用完整性，处理工作区和会话身份映射，并保留不确定执行状态。密钥与授权不能随着普通备份随意传播。
- **分析路径**：做完整恢复演练，而非只检查压缩包生成；再测试旧版本、损坏文件、重复导入和运行中快照的限制。
- **Trade-off**：完整快照恢复方便，但体积大且可能包含私有资料；选择性导出更可控，却需要明确缺失哪些依赖。
- **项目依据**：[备份服务](../../src/backup-service.ts)、[桌面工作区恢复](../../desktop/core/workspace-backup.ts)、[备份测试](../../tests/workspace-backup.test.ts)、[会话迁移测试](../../tests/desktop-migration.test.ts)。
- **追问 / 易错点**：备份副本不能算新的独立教学样本；恢复也不能自动恢复已撤销授权。

<a id="q46"></a>

### Q46：Electron 应用如何防止渲染内容获得本机权限？

- **口述答案**：知行开启 contextIsolation 和 sandbox，关闭 nodeIntegration；preload 只暴露有限命令，主进程继续校验命令和发送方，不能因为 UI 看起来可信就放过 IPC。
- **分析路径**：检查窗口配置、导航限制、IPC 入口、参数 schema 和敏感能力去向；模型 Markdown 与引用均视为不可信内容。
- **Trade-off**：限制桥接能力增加接口设计工作，但避免渲染漏洞直接扩大成本机任意操作。[Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security)
- **项目依据**：[主进程](../../desktop/electron/main.ts)、[preload](../../desktop/electron/preload.ts)、[IPC 契约](../../desktop/core/contracts.ts)、[前端边界检查](../../tests/frontend-boundary.ts)。
- **追问 / 易错点**：TypeScript 类型不能验证来自被攻击渲染进程的运行时输入。

<a id="q47"></a>

### Q47：API Key 存系统安全存储，为何还要关心签名和重复授权？

- **口述答案**：操作系统可能按应用身份限制密钥访问；开发构建身份变化会影响信任。知行桌面用加密安全存储，保留旧钥匙串兼容读取，并有固定本地签名流程；不把 Key 放进公开连接配置或模型上下文。
- **分析路径**：分清“Key 是否存在”的元数据检查和“实际解密/读取”，再核实应用签名、安装路径与迁移链路，避免把每次状态刷新都变成密钥读取。
- **Trade-off**：强系统保护可能带来授权交互；稳定身份和最小读取可以改善体验，但不能保证绕过所有系统提示。
- **项目依据**：[desktopSecrets](../../desktop/electron/secrets.ts)、[加密存储](../../desktop/core/secrets.ts)、[本地签名说明](../macos-local-signing.md)、[钥匙串测试](../../tests/macos-keychain.test.ts)。
- **追问 / 易错点**：本地签名与正式发行签名、公证是不同条件；不能声称全部跨平台安全存储已等价验收。

<a id="q48"></a>

### Q48：MCP 接入了可信服务，为什么仍要校验描述、输入和权限？

- **口述答案**：MCP 是工具通信协议，不自动提供宿主授权和内容可信保证。工具描述与返回内容可能含有注入，工具声明的风险也不是宿主权限依据；宿主仍应限制 schema、网络、进程、路径和结果。
- **分析路径**：把发现、展示、用户授权、执行与结果使用分开；新发现工具也必须受既有单调限制，不能通过重新发现绕过策略。
- **Trade-off**：丰富工具提高能力，也扩大攻击面与上下文负担；按需发现、最小权限和可审计结果优于一次暴露所有工具。
- **项目依据**：[MCP 连接](../../src/mcp-connection.ts)、[惰性发现](../../src/lazy-mcp.ts)、[MCP 工具](../../src/mcp-tools.ts)、[隔离测试](../../tests/mcp-isolation.test.ts)。[MCP 官方规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- **追问 / 易错点**：不能把服务端自报只读当作安全证明，也不能把 Prompt 里的拒绝规则当作 OS 沙箱。

## 九、评测与质量保证（49—54）

<a id="q49"></a>

### Q49：Agent 测试金字塔应包含哪些层？

- **口述答案**：先测确定性契约与状态机，再测工具/协议集成、故障恢复、实际 UI，最后用冻结任务做真实模型评测和学习者效果验证。每层回答不同问题，不能用测试数量替代质量证据。
- **分析路径**：把输入、执行轨迹、最终结果和评分分别保存；离线测试可覆盖大量故障，真实评测验证实际模型行为。Agent 评测需要关注环境与执行轨迹，而非只看最后文本。[官方工程讨论](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- **Trade-off**：全部真实调用昂贵且随机；全部 Mock 又无法代表模型质量。分层能兼顾复现和外部真实性。
- **项目依据**：[测试指南](../TESTING.md)、[通用架构验收](../evidence/provider-architecture-20260911.md)、[质量评测](../../src/quality-evaluation.ts)。
- **追问 / 易错点**：814 项是已记录工程门禁结果，20 次是更早构建的真实实验；不能合并成“834 道真实模型题通过”。[60570bc 的 GitHub CI](https://github.com/muzigef/zhixing/actions/runs/34576546164) 曾在团队 UI 发送按钮 disabled 处超时；后续已复现为按钮改名早于弹窗关闭的测试竞态。应展示受控延迟及等待真实 dialog 状态的[回归证据](../evidence/ci-44-team-ui-20260911.md)，不能用另一次偶然通过证明问题消失。

<a id="q50"></a>

### Q50：怎样公平比较团队与单 Agent？

- **口述答案**：固定题目、模型身份、资料、评分和失败口径；同时报告默认产品配置与相近计算预算两类对照。加入单模型自检基线，避免把多花几倍调用的收益全部归因于团队。
- **分析路径**：记录分工、实际档位、请求数、token、耗时、截断与失败；盲化候选顺序；不得只挑成功结果。
- **Trade-off**：相同次数不等于相同成本，相同 token 也不等于相同推理能力；应报告多个资源维度，而非宣称绝对公平。
- **项目依据**：[团队评测器](../../src/team-evaluation.ts)、[冻结用例](../../src/team-evaluation-cases.ts)、[质量协议](../agent-team-quality-evaluation-protocol-20260909.md)、[评测测试](../../tests/team-evaluation.test.ts)。
- **追问 / 易错点**：同一难题对四种模式运行四次，统计上不是四个独立题目。

<a id="q51"></a>

### Q51：历史结果从 18/20 到 20/20，可以在简历上写“准确率提升 10%”吗？

- **口述答案**：不宜。这里是四道冻结题在不同组的运行总数，且成功口径包含完成、答案字段正确和有解释；不是 20 道独立题。更合适说“修复特定预算截断案例，有限回归由 18/20 改善到 20/20”，并附实验限制。
- **分析路径**：核实分母、独立样本、版本、网络和随机变化；区分百分点、相对比例与统计显著性；更多独立题与重复运行后再估计稳定收益。
- **Trade-off**：小实验便宜、能发现回归，却不能支持总体胜率或教学因果结论。
- **项目依据**：[原始口径与限制](../evidence/team-resource-budget-20260911.md)、[解释复核](../evidence/team-resource-budget-review-20260911.json)。
- **追问 / 易错点**：20/20 也仍存在两处单模型教学措辞问题；“有解释”不等于“解释完全正确”。

<a id="q52"></a>

### Q52：LLM-as-a-judge 怎样避免自夸、顺序和长度偏差？

- **口述答案**：先给明确 rubric 和可核验参考，再对候选匿名、随机顺序、限制无关冗长影响，并与人工标注校准。可客观计算的答案字段优先用确定性检查；评审模型不能因与自己相似就判优。
- **分析路径**：测交换顺序是否变分、不同评审是否一致、错误解释是否高分；保留评语与证据，隔离题目中试图操纵评审的指令。
- **Trade-off**：模型评审扩展性好，但有相关偏差；人工成本高，也需要规范。知行当前开发侧解释复核不能说成独立人类盲评。
- **项目依据**：[团队质量评测](../../src/team-quality.ts)、[盲评实现](../../src/outcome-blind-review.ts)、[盲评测试](../../tests/outcome-blind-review.test.ts)、[历史解释复核](../evidence/team-resource-budget-review-20260911.json)。
- **追问 / 易错点**：项目的学习者解释盲评与团队答案开发复核是两条不同链路，不要混用验收结果。

<a id="q53"></a>

### Q53：真实失败案例如何变成回归测试，且不“教会模型考试”？

- **口述答案**：先保留原始失败输入、轨迹、环境和版本，提炼确定性的协议或状态错误，再添加测试；模型行为部分采用训练/开发集与保留集分离，避免不停用同题调 Prompt 后宣称泛化提升。
- **分析路径**：分别建立解析、执行、答案和质量回归；评分规则冻结，修改评分器必须说明为什么，不许为当前输出降低要求。
- **Trade-off**：固定题便于比较，但易过拟合；新题提升外部有效性，却增加标注和运行成本。
- **项目依据**：[团队质量用例](../../src/team-quality-cases.ts)、[质量保留集](../agent-quality-heldout.json)、[质量评测测试](../../tests/agent-quality-eval.test.ts)、[评测协议](../agent-team-evaluation-protocol-20260909.md)。
- **追问 / 易错点**：修改 Prompt、预算和评分器后同时变好，不能直接判断是哪一项带来的效果。

<a id="q54"></a>

### Q54：Agent 的故障注入应该优先覆盖哪里？

- **口述答案**：优先覆盖不可逆或可能重复的边界：工具派发前后、预算预留后、结果落盘前、进程中断、取消与最终验证竞争、权限撤回和旧版本恢复。
- **分析路径**：每个注入点都断言最终状态、是否新增副作用、预算是否保留、是否能确定性恢复，而非只断言抛了异常。
- **Trade-off**：故障矩阵复杂，但比单纯提高文本断言数量更能提高可靠性；可按副作用风险排序覆盖。
- **项目依据**：[崩溃测试](../../tests/agent-crash.test.ts)、[恢复边界](../../tests/agent-recovery-boundaries.test.ts)、[团队崩溃](../../tests/team-crash-recovery.test.ts)、[权限测试](../../tests/agent-permissions.test.ts)。
- **追问 / 易错点**：工具返回一段“cancelled”文本不能被信任为运行时取消元数据；取消状态必须由执行层掌握。

## 十、教学差异化与生产演进（55—60）

<a id="q55"></a>

### Q55：已有成熟通用 Agent，为什么还做知行？

- **口述答案**：通用 Agent 提供执行和推理能力，知行的差异在资料驱动学习、实际作答记录、按证据给教学建议、实践项目与延迟保持验证。价值应由用户是否学会和能迁移证明，而非更长的回答。
- **分析路径**：把用户结果拆成理解、独立完成、迁移与保持；模型和执行内核尽量通用，教学业务保持清晰。
- **Trade-off**：领域约束降低通用性，但能形成可测闭环；若没有真实效果证据，就只能说提供了验证能力，不能说效果领先。
- **项目依据**：[教学政策](../../src/teaching-policy.ts)、[实际作答](../../src/learning-observations.ts)、[效果验证](../../src/learning-outcomes.ts)、[项目实践](../../src/practice-projects.ts)。
- **追问 / 易错点**：把“对齐 Codex 架构”与“产品定位为编程代理”混为一谈；知行使用通用内核服务学习目标。

<a id="q56"></a>

### Q56：模型判断“用户已经掌握”可以直接写入学习状态吗？

- **口述答案**：不能。知行区分用户命令、模型提议与分类，并要求相应确认或用户证据；教学策略依据真实作答及帮助方式给建议，不把一次答对升级为整体掌握。
- **分析路径**：追踪事实来源、是否独立作答、是否被提示、是否后来纠正；保留撤回和更正机制。
- **Trade-off**：显式证据比模型自动画像繁琐，但更少误判和长期污染；可用轻量交互收集证据，不能省略证据标准。
- **项目依据**：[会话政策](../../src/conversation-policy.ts)、[TeachingPolicy](../../src/teaching-policy.ts)、[学习观察测试](../../tests/learning-observations.test.ts)、[政策测试](../../tests/teaching-policy.test.ts)。
- **追问 / 易错点**：模型自行生成一道题又自行判断用户掌握，缺少独立学习者行为。

<a id="q57"></a>

### Q57：知行怎样测“学会了”，而不是“答案生成得好”？

- **口述答案**：现有流程包含前测、学习、后测和三天后延迟测，使用不同题卷次序，记录是否独立作答、模型条件、课堂证据与构建来源；解释需要独立复核，未完成或条件变化的数据保留并标记。
- **分析路径**：先看前测基线与后测变化，再看延迟保持和迁移；区分 prompt_only 与 full_product，避免把提示方式试验称为完整产品验证。
- **Trade-off**：延迟测更贴近保持效果，但有流失与日程成本；短期满意度容易收集，却不能替代学习结果。
- **项目依据**：[LearningOutcomeStore](../../src/learning-outcomes.ts)、[试验契约](../../src/outcome-contracts.ts)、[学习效果测试](../../tests/learning-outcomes.test.ts)、[协议](../teaching-study-protocol.md)。
- **追问 / 易错点**：题卷顺序随机不代表参与者已随机分组；当前真实教学因果收益尚未得到证明。

<a id="q58"></a>

### Q58：自选使用知行的人后测更高，为什么仍不能证明产品有效？

- **口述答案**：用户可能本来更有动力、基础不同、学习更久或看过相同题；自选分组存在混杂。当前汇总明确是描述性结果，排除重复、辅助作答和条件变化也不能消除所有偏差。
- **分析路径**：先检查样本来源、去重、流失和分组；若做因果试验，预先定义指标，随机分配条件并控制学习时长，处理延迟测缺失。
- **Trade-off**：严格对照更能回答效果问题，但组织成本高；真实使用数据外部环境更自然，却难识别因果。
- **项目依据**：[summarizeOutcomes](../../src/learning-outcomes.ts)、[导出合并限制](../../src/outcome-report.ts)、[结果报告测试](../../tests/outcome-report.test.ts)。
- **追问 / 易错点**：多个备份、多个试验记录不一定对应多个独立学习者；项目没有核实身份的参与者去重体系。

<a id="q59"></a>

### Q59：当前最重要的生产差距是什么？你会如何排序？

- **口述答案**：先统一 CLI 输入限额差异，并保持已修正的 CI 团队测试竞态回归，再扩大真实质量评测与独立学习者验证，按发布需求补正式发行与平台验收。新厂商、Gemini、SDK/App Server 按需扩展。云化另需多租户身份、队列、配额和隔离，不能把本地程序直接包装成 SaaS。
- **分析路径**：按用户风险、证据缺口、依赖条件和可交付范围排序；先验证价值，再投入不必要的基础设施。
- **Trade-off**：过早做云化和所有厂商增加维护成本；只保持本地模式限制协作与运维能力。选择应服从用户和规模，而非技术清单。
- **项目依据**：[当前接入边界](../provider-architecture.md)、[通用验收](../evidence/provider-architecture-20260911.md)、[桌面部署说明](../../desktop/README.md)、[效果协议](../teaching-study-protocol.md)。
- **追问 / 易错点**：不要把“架构允许扩展”写成“已服务百万用户”，也不要把本地签名描述为正式商业发行全部完成。

<a id="q60"></a>

### Q60：面试时如何讲清这个项目，同时不夸大自己的贡献？

- **口述答案**：用“用户问题—关键决策—实现责任—失败案例—验证证据—剩余边界”展开。讲自己确实能解释和复现的模块，说明 AI 辅助开发的范围以及自己如何审查、测试和纠正，不把生成代码量当主要贡献。
- **分析路径**：选一个可深入追问的案例，例如成员预算耗尽；展示先前失败、诊断证据、资源策略、定向测试与真实回归，再解释结论为什么有限。
- **Trade-off**：真实边界看起来少一些“成绩”，却更经得住追问；宽泛地说架构对齐顶尖产品很难验证。
- **项目依据**：[架构契约](../provider-architecture.md)、[预算实验](../evidence/team-resource-budget-20260911.md)、[工程验收](../evidence/provider-architecture-20260911.md)、[口述与简历模板](system-design.md)。
- **追问 / 易错点**：任何“我实现/我设计”都要与本人实际参与相符。团队或 AI 协作成果应说明职责，无法复现的数字不要放进简历。

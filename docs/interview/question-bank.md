### Q01：什么是 Agent？知行与固定工作流的边界在哪里？

- **口述答案**：Agent 是在目标、上下文和权限约束内，由模型决定下一步工具或回答的执行系统。知行的工具选择有模型自主性，但权限、预算、持久化和终止条件由代码控制；学习效果试验则采用明确状态机。产品不需要把每一步都交给模型决定。
- **知行具体怎么做**：以“根据当前主题资料解释缓存”为例，请求先到 AgentService；assistant-runtime 按会话授权构造上下文与工具列表，模型提出检索调用后，由 ToolHarness 校验并执行，结果再交回模型续答。模型不能自己扩大权限或取消轮数上限。教学效果试验另由 LearningOutcomeStore 控制前测、学习、后测、延迟测验的阶段，不能靠一句“已完成”跳过。
- **分析路径**：先判断任务路径是否可预先枚举；再识别需要推理的分支；最后把不可违反的不变量放到执行器。Anthropic 也将预定义编排与模型动态决策区分开。[官方说明](https://www.anthropic.com/engineering/building-effective-agents)
- **Trade-off**：动态决策提高适应性，也增加不可预测性和验证成本；固定流程更可测，但难覆盖开放任务。知行使用混合方案。
- **追问**：模型输出一个计划就算 Agent 吗？工具循环越多，自主性就越强吗？
- **追问答案**：一个计划只是文本产物；还要看系统能否执行允许的动作、读取反馈，并根据结果调整下一步。知行会保存工具调用与结果，越权动作被拒绝，超限或重复调用会停止相应执行。自主性体现为在约束内选择有效动作，反复调用相同工具却没有新信息，通常是缺乏进展。

### Q02：Transformer 和自回归推理与 Agent 延迟有什么关系？

- **口述答案**：注意力机制根据上下文构造 token 表示；常见自回归生成根据已有内容逐步预测后续 token。应用侧一次调用的输入长度、输出长度、思考量和调用次数都会影响体验。知行负责调用和执行控制，没有训练 Transformer 或实现推理引擎。
- **知行具体怎么做**：知行没有实现模型推理引擎。应用先用 modelContextWindow 减少不必要的历史，再在调用时记录上下文、模型和工具耗时；Pi 路径还记录启动、首事件、首正文和退出清理时间。例如用户感到“等很久才出字”，应先看是否卡在进程启动、请求等待或工具执行，而不是直接归因于模型计算慢；首事件也可能只是状态通知。
- **分析路径**：先区分模型计算与网络/进程时间，再区分处理输入与逐步生成。KV cache 可复用已有注意力键值计算，但它不等于应用的对话记忆，也不自动跨用户共享。[Transformer 原论文](https://arxiv.org/abs/1706.03762)、[生成与缓存参数](https://huggingface.co/docs/transformers/main/en/main_classes/text_generation)
- **Trade-off**：减少输入可节约计算，却可能丢失任务条件；压短输出可降低等待，却可能破坏解释。应保留必要信息并实测。
- **追问**：能根据客户端总耗时，反推出 GPU 利用率或模型处理输入的时间吗？
- **追问答案**：不能。客户端总耗时混合了本地准备、网络往返、远端排队和生成等阶段；知行的 requestMs 也包含认证解析、网络及远端处理。只有服务端提供对应指标，才能进一步拆分。现有观测适合定位客户端看到的等待区间，不能当作 GPU 性能报告。

### Q03：上下文窗口、输出上限、字符上限、计费 token 是一回事吗？

- **口述答案**：不是。上下文窗口约束模型能处理的输入与生成空间；输出上限约束该请求允许生成多少 token；字符上限是应用保护边界；实际用量由服务商或官方运行时报告。知行的字符估算只用于调度，不能当账单。
- **知行具体怎么做**：发送前，modelContextWindow 把消息、工具定义、完整工具历史和图片估算一起计入输入，并预留输出空间；默认本地窗口政策为 48,000、输出预留为 16,384。estimateTokens 对 ASCII 与非 ASCII 使用不同的粗估权重；适配器再用自身能力收紧预算。实际用量另存 ModelUsage，不能把字符数或这套粗估直接换算成账单。
- **分析路径**：核实协议对输入、推理、正文的定义；为输出预留空间；计入工具定义、完整工具轮次、图片和当前输入；记录估算与实际报告的差异。
- **Trade-off**：保守估算会少利用窗口，但减少超限失败；激进估算可能省一次摘要，却增加重试与状态恢复成本。
- **追问**：48,000 是所有模型的官方窗口吗？原生 CLI 的字符上限能当作硬 token 限额吗？
- **追问答案**：都不能。48,000 是知行的本地调度上限，底层模型的实际限制需由适配器或配置确认；原生执行器的能力标为输出限额未知。限制返回字符数只能约束应用接收的文本，不能保证运行时没有生成更多内容，也不能约束隐藏推理的 token 消耗。
- **源码与测试索引**：[estimateTokens 与 modelContextWindow](../../src/context-window.ts)、[ModelCapabilities](../../src/model-capabilities.ts)、[图片预算](../../src/image-input.ts)、[预算测试](../../tests/agent-context-budget.test.ts)、[请求与用量契约](../../src/model.ts)。

### Q04：temperature、top-p 和思考档位分别控制什么？

- **口述答案**：temperature 改变采样分布的集中程度，top-p 限定候选概率质量；思考档位是具体模型协议对推理投入的控制。它们不是同一旋钮，也不能保证低温输出正确或跨服务商完全确定。[生成参数定义](https://huggingface.co/docs/transformers/main/en/main_classes/text_generation)
- **知行具体怎么做**：共享请求只暴露 quick、balanced、deep，没有通用的 temperature 或 top-p 调节字段。Chat Completions 适配器按配置的推理协议映射请求，例如 quick 在 DeepSeek 路径关闭 thinking，在 Kimi 路径发送 low。团队只对声明推理与正文共用预算的成员计算资源策略；若用户显式选 deep，额度不足也保留该选择，并记录 budgetLimited。
- **分析路径**：先确认适配器实际支持哪些参数，再看发送出去的请求。知行向业务暴露 quick、balanced、deep，由适配器映射，不声称这些名字对应相同算力。
- **Trade-off**：任务需要可靠结构时可减少采样波动；需要探索时可允许多样性，但必须独立校验。模型不支持的参数应拒绝或不暴露。
- **追问**：接口里有参数，就说明所有服务商支持且含义一致吗？知行有统一温度调优器吗？
- **追问答案**：没有统一温度调优器，字段存在也不构成服务商能力证明。同一个 balanced 在不同适配器中可能变成不同请求值，应检查实际请求及连接验收。协议测试验证的是代码如何映射和续传状态；它不能证明相同名字对应相同推理投入，更不能保证回答正确。
- **源码与测试索引**：[ReasoningProfile](../../src/model.ts)、[Chat Completions 适配](../../src/chat-completions-client.ts)、[成员资源策略](../../src/team-resource-policy.ts)、[推理协议测试](../../tests/provider-reasoning.test.ts)。

### Q05：模型“思考完却没有答案”是否说明账户没钱？

- **口述答案**：不能直接判断。先区分 HTTP/认证失败、超时、输出截断和预算耗尽。此前异模型团队中，推理与正文共用输出额度，成员可能用尽额度却没形成完整报告；这是生成资源问题，与余额不足是不同故障。
- **知行具体怎么做**：memberResourcePolicy 先为规划、审查和最终回答留预算，再计算每位成员的输出上限。只有能力声明为 shared-output 时，才根据余量调整继承的思考档位；显式设置保持不变。测试用“只返回推理、结束原因是 length”的合成响应复现报告被截断，并检查失败仍可见。真实历史中的连接拒绝则单独记录，不能混算为预算不足。
- **分析路径**：看结束原因、推理/正文用量、实际提交档位、单次上限和剩余总预算，再重现固定题。不能仅凭 UI 没答案猜测原因。
- **Trade-off**：增加额度提升完成机会，但增加时延与费用；降低自动思考档位可能更快，也可能增加推理错误，需要审查补偿。显式用户设置优先。
- **追问**：4096、8192、16384 是厂商规定的最低正确答案预算吗？预算不足是否应偷偷调大？
- **追问答案**：这些数字是知行给 quick、balanced、deep 设置的调度目标，不是答案正确性的门槛。增加输出空间可能帮助完成报告，但仍可能推理错误或耗尽额度。项目不会越过用户总预算；自动策略仅调整未显式指定的成员档位，显式选择导致的不足要如实保留并反馈。
- **源码与测试索引**：[预算策略](../../src/team-resource-policy.ts)、[策略测试](../../tests/team-resource-policy.test.ts)、[历史预算实验](../evidence/team-resource-budget-20260911.md)。

### Q06：改 Prompt、做 RAG、微调和换模型，如何选择？

- **口述答案**：先分类失败。输出要求不清先修提示与契约；缺少外部事实先改检索；执行失败先改工具和状态机；稳定的行为分布问题才考虑用数据做微调。换模型要用冻结评测判断，不以品牌替代诊断。
- **知行具体怎么做**：知行把教学提示、DocumentLibrary 检索和质量评测分开。若“缓存失效”找不到英文资料，可先检查查询扩展和候选排序；若片段已找到却杜撰提升比例，应查证据检查与提示约束；若工具一直重复，则查执行循环。evaluateQuality 保存题集哈希、回答及待人工复核状态，方便对照修改；当前没有微调训练与部署流水线。
- **分析路径**：收集错误样本，固定基线，每次改变一个主要因素，并记录成本与回归。RAG 原始工作将外部检索与生成结合，但检索成功仍不保证回答忠实。[原始论文](https://arxiv.org/abs/2005.11401)
- **Trade-off**：Prompt 迭代快；RAG 易更新知识但增加检索链路；微调需要训练数据、部署和评测成本。知行当前没有微调流水线。
- **追问**：RAG 能彻底消除幻觉吗？能把微调当成实时知识库吗？
- **追问答案**：不能。检索只把候选资料提供给生成过程，仍可能漏证据、找错版本或误读原文；知行因此另做引用和数值检查。微调主要调整模型行为，知识更新还需要数据与训练过程。对经常变化且需要出处的资料，应优先维护检索与版本链；这也不等于已经证明 RAG 总是更优。

## 二、接入与可扩展架构（07—12）

<a id="q07"></a>

### Q07：为什么同时需要 ModelClient 和 AgentExecutor？

- **口述答案**：ModelClient 返回逐轮模型事件，知行负责工具执行和续轮；AgentExecutor 返回外部 Agent 的完整任务结果。两者合为 AgentBackend，共享业务内核，但保留执行责任差异，避免外部工具已执行后被知行重复执行。
- **知行具体怎么做**：assistant-runtime 先判断后端类型：ModelClient 路径进入 collectInvocation，收齐工具调用后由知行执行，再通过 continue 续轮；AgentExecutor 路径则先裁剪文本上下文，再 prepare、execute，检查完整结果。当前原生 Codex/Claude 适配禁用工具，只接收受限文本任务；返回 completed 仍标为 unverified，表示运行结束，并未证明答案正确。
- **分析路径**：从“谁掌握工具循环”划分接口，而不是从“是不是 HTTP”划分。再明确 prepare、取消、上下文、输出和用量契约。
- **Trade-off**：一个万能 stream 接口表面简单，却容易隐藏工具所有权；双接口增加类型分支，但让安全和预算语义清晰。
- **追问**：AgentExecutor 可扩展，是否意味着现在能直接使用外部 Agent 的全部工具能力？
- **追问答案**：不能。接口表达的是执行责任如何交接，当前实现只开放受限文本任务，没有开放外部文件或 shell 工具。以后若扩展工具能力，还需明确谁授权、谁执行、如何记录副作用及恢复。否则外部已经做过的动作，可能又被知行当作待执行调用重复处理。
- **源码与测试索引**：[AgentBackend](../../src/agent-executor.ts)、[ModelClient](../../src/model.ts)、[统一入口](../../src/agent-service.ts)、[架构边界测试](../../tests/agent-architecture-boundary.test.ts)、[后端分流](../../src/assistant-runtime.ts)。

<a id="q08"></a>

### Q08：怎样做到新增第十一家模型时不用修改业务代码？

- **口述答案**：若兼容已支持协议，就新增连接配置，提供地址、模型、能力和密钥引用；若是新协议，则实现 ModelClient；若是新官方 Agent 运行时，则实现 AgentExecutor 或 NativeRuntimeAdapter。厂商目录只是配置模板，不是白名单。
- **知行具体怎么做**：动态连接经过 apiConnectionInputSchema 校验，保存协议、地址、模型、能力和密钥引用；createAgentModel 按协议创建 ChatCompletionsClient 或 ProtocolModelClient，业务仍调用同一 AgentService。已有三种协议能覆盖的新增厂商可走配置；新原生协议则接 NativeRuntimeAdapter 注册表。目录外合成厂商测试验证这条扩展路径，未代表真实厂商已验收。
- **分析路径**：将“品牌名”“传输协议”“模型能力”“认证方式”拆开；通过工厂与注册表注入；用目录外合成厂商验证扩展路径。
- **Trade-off**：配置化覆盖常见差异；复杂认证和协议差异需要代码。把所有差异做成任意脚本配置会牺牲审查与安全边界。
- **追问**：通用连接架构是否意味着任意网站订阅都能直接作为 API 使用？
- **追问答案**：不是。网站订阅、API 密钥和官方 Agent 运行时是不同接入方式，能配置协议不代表拥有相应服务权限。知行只对已有协议复用客户端，新认证或运行时仍需官方支持依据和独立适配验收。合成扩展测试证明业务无需按品牌改写，不证明新厂商的账号、计费或工具能力。

### Q09：为什么不能仅根据模型名称判断图片、工具和窗口能力？

- **口述答案**：名称可能映射到不同版本、代理或套餐。知行把能力显式放入连接与适配器，在发请求前检查图片、工具续轮和预算。能力声明是受控配置，仍需连接级验证。
- **知行具体怎么做**：ModelCapabilities 显式描述图片、工具调用、续轮和窗口政策。动态连接的 images、tools 与预算字段参与适配器能力构造；AgentService 在图片发送前拒绝文本模型，调用层再核对有效预算。比如中转连接只支持文字，就不能因名称含有某个多模态型号而发送图片。内置适配也有兼容规则，但仍是应用政策。设置中可分别运行文本和最多两轮合成工具往返探针，回执区分声明与观测；实际模型名只取服务端返回，未报告保持未知。原生 CLI 单列运行时版本与兼容依据，不能把文本通过推广到图片、窗口或所有工具能力。
- **分析路径**：先确定实际模型身份，再检查所需能力，最后限制在应用政策与服务商能力的交集内。
- **Trade-off**：保守拒绝会减少“试试看”的便利；盲目发送可能丢图片、错处理工具或产生隐藏费用。可通过预检改善体验。
- **追问**：模型官方支持工具，就能证明中转服务支持并行工具和续轮吗？
- **追问答案**：不能。中转可能删掉工具 ID、丢失续轮状态，或把分段参数拼错。应针对这个连接测试完整调用、结果回传、多个工具、截断和取消等情形；只测普通文本成功是不够的。知行使用明确能力声明做预检，再用协议测试覆盖处理路径，但不能据此给任意中转背书。

### Q10：订阅账号为何通过官方运行时，而不是复制登录 token？

- **口述答案**：让官方运行时管理其认证生命周期，知行管理任务上下文和受控进程。这样避免把服务商私有登录状态变成应用持久密钥，也不在订阅失败时静默改走付费 API。
- **知行具体怎么做**：NativeAgentExecutor 在临时目录运行官方程序，使用固定参数数组和 shell: false，并过滤继承环境；适配器负责版本、隔离条件和官方登录状态检查，知行不复制订阅 token。当前目录把 Codex 标为可用于团队，Claude 仅有单 Agent 适配，Gemini 没有执行适配。已有 Codex 文本与团队历史验收，不能据目录里出现三个名字说三家已打通。
- **分析路径**：明确认证所有者、执行所有者和计费通道，再验证官方程序版本、权限隔离、输入输出和终止行为。
- **Trade-off**：官方 CLI 更容易复用既有登录，但有启动成本、版本漂移及事件契约依赖；SDK/App Server 可降低某些生命周期成本，但需单独评估和实现。
- **追问**：Codex、Claude Code、Gemini 的原生接入现在分别验证到了哪里？
- **追问答案**：Codex 已有官方订阅文本执行和团队接入的历史验收。Claude Code 的单 Agent 适配代码及合成测试存在，但真实账号未验收，团队未开放。Gemini 原生执行器尚未实现；Gemini API 支持属于另一条连接路径。这次文档核对没有重新登录，也没有重跑真实模型请求。

### Q11：三种 API 协议怎样统一流式回答与工具调用？

- **口述答案**：传输层处理分帧、UTF-8、取消和总量上限；协议解码器维护工具与内容状态，再输出统一 ModelEvent。完整的工具请求才进入执行边界，连接特有的续轮状态保留在调用历史中。
- **知行具体怎么做**：provider-http 用流式 UTF-8 解码和大小上限读取帧；MessagesDecoder、ResponsesDecoder 或 Chat Completions 客户端积累文本与工具参数，确认协议结束状态后才输出完整 tool_call。续轮时保留与模型、连接绑定的不透明 provider_state，也就是适配器保存但业务不解释的协议数据。测试覆盖分段参数、重复调用 ID、截断以及失败仍带用量的情况。
- **分析路径**：分别测试半帧、多帧、工具参数跨片段、重复事件、结束标志、截断和用量缺失；不能把每个 SSE 片段直接作为可执行 JSON。
- **Trade-off**：统一事件方便业务复用，但不能丢失协议必须回传的状态。保留不透明状态比强行扁平化更安全。
- **追问**：HTTP 200、连接结束、done 事件是否都等于工具调用和回答完整成功？
- **追问答案**：不等于。HTTP 200 只表示拿到了成功状态的响应，流仍可能半途断开或报告输出截断。协议解码器必须检查完成标志与工具参数是否齐全，未完成时不能派发那批工具。即使用量已返回，也应保留消费记录并将本轮标为未完成，不能把计费信息当成功证明。
- **源码与测试索引**：[HTTP 帧读取](../../src/provider-http.ts)、[协议编解码](../../src/protocol-codecs.ts)、[协议客户端](../../src/protocol-model-client.ts)、[协议测试](../../tests/provider-protocols.test.ts)。

### Q12：为什么任务恢复要冻结模型身份和连接？

- **口述答案**：恢复应延续原任务的执行条件。若配置中的模型、连接、权限范围或预算策略改变，就不能悄悄把后半程交给另一套条件；应阻止不兼容恢复或创建新任务。
- **知行具体怎么做**：以团队中断后继续为例，bindAgentModel 先冻结可动态解析的客户端，再绑定 provider、model、connection 和 reasoning；存在旧记录时逐项比较，不匹配报 team_model_mismatch。原生团队还拒绝 auto 等未固定模型身份。TeamCoordinator 同时保留旧范围、配置与成员资源策略，因此用户改了当前偏好，也不能悄悄把旧任务变成一次新模型实验。
- **分析路径**：绑定 provider、model、connection、reasoning 等身份，保存配置与上下文范围摘要，恢复时比较，再加载已经完成的产物。
- **Trade-off**：冻结降低运行中热切换灵活性，但提高可追溯性、实验公平性和故障解释能力。
- **追问**：配置显示名没变，就能证明底层模型没变吗？供应商更新同名模型怎么办？
- **追问答案**：不能。知行能比对的是连接和适配器公开的模型身份；供应商在同一别名后更换权重，未必会被本地身份比较发现。应记录可获得的实际版本与运行条件，重要回归重新评测。冻结绑定防的是应用静默换连接或档位，并不构成对远端权重永远不变的保证。

## 三、状态、记忆与上下文（13—18）

<a id="q13"></a>

### Q13：知行有哪些不同的“记忆”？

- **口述答案**：至少区分原始对话、当前模型窗口、会话摘要、来源明确的长期记忆、学习画像/实际作答记录，以及执行检查点。它们分别服务于回看、生成、衔接、检索、教学和恢复，不能共用一个不断增长的 Prompt。
- **知行具体怎么做**：用户发来新问题后，AgentService 从会话记录构造本轮窗口；授权后 LearningContextBuilder 再读取当前主题画像、相关长期记忆和教学检查点。会话摘要只帮助衔接较早对话；AgentExecutionStore 保存工具轮次与未完成调用，供中断恢复。比如“上次改了什么”应查原始记录或执行回执，不能把摘要中的“应该修改”当成实际完成。
- **分析路径**：为每类数据定义来源、范围、生命周期、撤销方式和读取权限；模型总结不能直接升级为用户事实或完成状态。
- **Trade-off**：分层增加数据关联复杂度，但能控制污染、撤销和窗口成本；全量拼接实现简单却难长期维护。
- **追问**：模型 KV cache、会话摘要、长期记忆为什么不能混为一谈？
- **追问答案**：KV cache 是推理引擎内部复用计算的缓存，知行没有把它当应用事实库。会话摘要是对一段历史的压缩，会遗漏或误述；长期记忆则是应用按主题、来源和授权保存并检索的记录。清掉计算缓存不等于删除长期记忆，撤回用户记忆也不能只删摘要中的一句话。
- **源码与测试索引**：[学习上下文](../../src/learning-context.ts)、[会话存储](../../src/agent-session-store.ts)、[会话摘要](../../src/conversation-summary.ts)、[执行存储](../../src/agent-execution-store.ts)。

<a id="q14"></a>

### Q14：摘要有来源哈希，是否就能证明摘要正确？

- **口述答案**：哈希只证明摘要覆盖的源记录仍然匹配，不证明摘要忠实或语义正确。知行保存覆盖到哪条消息和源哈希，源记录变化后旧摘要不再作为有效覆盖。
- **知行具体怎么做**：planConversationSummary 保留最后八条消息原文，将更早未覆盖记录每批最多取二十四条生成摘要；summarySourceHash 对覆盖区间的消息 ID、角色、正文、状态和图片信息计算哈希。下一轮 verifiedSummaryThrough 重算后才承认覆盖。若用户改了区间内一句话，旧摘要不能继续当有效覆盖；生成或取消失败也不能推进到没读过的位置。
- **分析路径**：先校验来源范围，再判断是否需要新的摘要；关键目标、约束和实际执行状态通过结构化数据保留，不依赖摘要独自承担。
- **Trade-off**：摘要降低上下文成本但会遗漏信息；保存原文和来源边界提高可恢复性，却需要额外存储与校验。
- **追问**：哈希校验通过，为什么仍不能说摘要没有幻觉？应该怎样验证摘要忠实？
- **追问答案**：哈希只回答“这份摘要绑定的源记录是否还是同一批”，没有比较摘要里的主张是否来自原文。忠实度需要另看目标、纠正、条件和未完成事项是否保留，有无新增事实。现新增六组带纠正、冲突、否定条件、中断和引用注入的固定对话，eval:quality -- --summary 经实际后台整理导出摘要与源记录，再用哈希绑定的 quality-review 接收逐项评分；完成和范围检查不自动算语义通过。另将显式用户原文片段独立保留，降低对有损摘要的依赖。
- **源码与测试索引**：[summarySourceHash / verifiedSummaryThrough](../../src/conversation-summary.ts)、[摘要覆盖测试](../../tests/summary-coverage.test.ts)、[结构化上下文测试](../../tests/structured-context.test.ts)。

<a id="q15"></a>

### Q15：长对话超出预算时，为何不能从最早字符直接截断？

- **口述答案**：字符截断可能切断工具调用与结果，丢失用户纠正或破坏协议。知行生成一次性的模型上下文视图，优先移除完整较早工具轮次与可移除消息，保留系统信息、关键边界和当前待执行内容，原始记录不被改写。
- **知行具体怎么做**：modelContextWindow 先尝试移除较早的完整工具轮次，保留最新工具结果与 pending 调用；仍超限才移除可删的旧消息，保护系统消息、观察信息、首末用户消息和最后一条回答。它还插入遗漏条数与“不可猜测缺失事实”的提示，必要内容仍放不下就报 model_input_limit。这是本次发送视图，持久会话和执行回执不会随裁剪删除。
- **分析路径**：计算完整请求预算，保留不可拆分结构；仍无法容纳时明确失败，不能把一半工具结果交给模型继续执行。
- **Trade-off**：保留完整轮次可能比按字截断更早触发上限，但避免协议错误与执行重复。
- **追问**：UI 能看到完整历史，是否说明模型每轮都读到了全部历史？被省略的事实怎么办？
- **追问答案**：不能。UI 回看的是保存的原文，模型使用的是受预算限制的视图。知行会在视图中说明省略了多少消息或轮次；模型应查询可用的实际任务状态，或明确缺少信息，必要时请用户补充。不能为了维持对话流畅就补造旧承诺、旧结论，更不能据猜测重做可能已完成的写操作。
- **源码与测试索引**：[modelContextWindow](../../src/context-window.ts)、[上下文测试](../../tests/agent-context-budget.test.ts)、[恢复边界测试](../../tests/agent-recovery-boundaries.test.ts)、[消息视图构建](../../src/learning-agent-profile.ts)。

### Q16：长期记忆相关性和冲突如何处理？

- **口述答案**：先限制主题和授权，再按问题检索相关记录，并保留来源。知行对相关记忆做有界摘录，也覆盖同义表达；没有相关项时才使用近期回退。同等相关的记录按较新优先呈现，但并未实现通用事实冲突消解。
- **知行具体怎么做**：LearningContextBuilder 每轮按主题查询未删除记忆，最多选三条，每条用问题相关摘录限制为 1,500 字符并保留 sourceRef。database 先用同义词扩展做相关性排序，同分再按确认时间和插入顺序取较新记录；没有相关结果才回退近期项。显式 correct_memory 更正另建来源关系，被取代的旧记录停止召回；原文哈希防止竞争覆盖，撤回新记录不复活旧记录。没有明确更正关系的矛盾仍不会自动解决。
- **分析路径**：拆分“是否相关”“是否可信”“是否过时”，用冲突和撤回案例验证，不只检查简单关键词命中。
- **Trade-off**：只取最新记录会漏掉很早的关键事实；只看相关性会引入旧错误。需要来源、时间和用户纠正共同约束。
- **追问**：这套策略已经能推理所有事实冲突，或者等同知识图谱了吗？
- **追问答案**：没有。它提供主题隔离、相关性排序、新近性和来源线索；新记录时间较晚本身不代表旧记录无效；只有用户确认的明确更正建立取代关系，原记录仍保留来源。遇到相互矛盾的内容，仍要依据用户明确纠正或继续核实。知识图谱还涉及实体和关系建模，通用冲突推理也需要更多规则与验证，当前不能这样宣传。
- **源码与测试索引**：[LearningContextBuilder.snapshot](../../src/learning-context.ts)、[记忆检索](../../src/database.ts)、[记忆质量测试](../../tests/memory-recall-quality.test.ts)。

### Q17：如何从架构上保证桌面与 CLI 的记忆、权限策略相同？

- **口述答案**：两端作为传输和展示层，进入同一 AgentService 与 LearningApplication；上下文构建、授权和状态迁移留在共享模块。入口也必须使用共享契约：2026-09-18 已修复 CLI 独立的 8,000 字符提前限制，两端均使用 20,000 字符上限。
- **知行具体怎么做**：CLI 的普通聊天请求进入共享服务，桌面也把发送契约交给同一 AgentService；权限、资料读取、模型窗口和写入恢复都在共享层处理。统一政策测试覆盖撤权后两端不再带出记忆与教学数据。execute 与发送契约现在共用 MAX_INPUT_CHARACTERS；新增真实 CLI 子进程和桌面契约对照覆盖 8,001、20,000、20,001 字符。
- **分析路径**：检查是否存在某端绕过共享入口、私自拼 Prompt 或缓存旧授权；撤权后下一轮必须重新构建上下文。
- **Trade-off**：共享核心提高一致性，但两端 UI 表达可以不同；要求政策相同不意味着终端和桌面代码完全相同。
- **追问**：只复用同一个模型类够吗？应怎样验证 8,001—20,000 字符的入口差异？
- **追问答案**：不够，模型类只负责请求传输，不能替代上下文读取、授权与写回政策。应增加穿过真实 CLI 校验入口和桌面发送契约的对照用例，检查相同长输入在进入共享服务前后的结果。新增 input-entrypoints 测试已实际复现旧限制并验证修复；撤权测试继续单独覆盖授权，不能用一种测试代替另一种。

### Q18：长会话文件如何避免每次保存都越来越慢？

- **口述答案**：知行将较早消息按内容哈希分段保存，主文件保留段索引和尾部，读取校验段内容与会话身份；写入按会话串行并使用原子替换。它优化本地存储，不意味着拥有无限对话容量。
- **知行具体怎么做**：AgentSessionStore.save 将较早消息每二百五十条组成一个哈希段，旧段首次验证后缓存至多 512 个文件签名，未变化时避免重复读盘解析；变更、篡改和链接替换继续拒绝或重验。主文件保存段索引和最多二百五十条尾部消息，并按会话串行、临时文件替换写入。load 校验会话 ID、段哈希和大小，缺段或篡改则拒绝加载。save 仍会检查并遍历历史，因此主要减少旧内容重复写盘，不能说长会话保存已变成固定成本。
- **分析路径**：测量消息数增长下的序列化、磁盘写入、索引和 UI 渲染，再针对主导成本优化；同时保留大小上限。
- **Trade-off**：分段减少重复写入，增加段管理和损坏检查；单 JSON 易理解，但长会话重写成本更高。
- **追问**：二百五十条分段是否意味着无限容量或分布式日志？还有哪些开销没消失？
- **追问答案**：不是。它是本地 JSON 文件的组织策略；会话仍受消息条数及约 12 MB 序列化大小限制，没有跨机器复制或分布式一致性协议。保存仍要校验、序列化和计算历史段哈希，读取也需重组消息。2026-09-18 同机七次热保存测量中，20,000 条尾部修改的 P50 从 116.13 ms 降至 56.41 ms，历史段读取从 79 次降至 0；逻辑写入量未变，不将此结果冒称 UI 或跨平台加速。
- **源码与测试索引**：[AgentSessionStore](../../src/agent-session-store.ts)、[分段会话测试](../../tests/segmented-conversation.test.ts)、[会话扩展性测试](../../tests/session-scaling.test.ts)、[会话总量上限](../../src/input-limits.ts)。

### Q19：PDF / Markdown 导入时如何选择切块与元数据？

- **口述答案**：切块要保留可定位的页码或锚点，并保存文档、主题和内容版本。知行进行格式、大小、页数及重复检查；PDF 中无可提取文字的页面逐页尝试 OCR，低置信度不能伪装成可靠原文。
- **知行具体怎么做**：显式导入的资料经 DocumentLibrary 检查扩展名、哈希去重和配额：单文件最多 250 MiB、PDF 最多 500 页。Markdown 按围栏之外的标题分节，PDF 提取逐页文字并保留换行；切块默认 1,000 字符，尽量完整保留表格、公式、代码及相邻短前提。超限结构另存最多两个真实上下文块的关联，不在原文块中伪造或重复表头。保留页码、锚点、内容哈希与切块版本。无可提取文字的页逐页尝试 OCR；置信度低于 70 标为低置信度。混合页保留原文本，未识别页面持久记录为 ocr_partial，并进入引用和模型提示；重试只补未识别页。
- **分析路径**：先看文档结构与问题分布，再试不同块大小，分别测召回和最终回答。避免把公式、表格的关键条件拆散。
- **Trade-off**：小块定位精确但上下文不足；大块信息完整但噪声与 token 成本更高。结构化切块和重叠参数应由评测驱动。
- **追问**：现在能保证正确解析所有 PDF 表格、复杂版面和扫描页吗？
- **追问答案**：不能。PDF 文本提取仍按页组织，现已实现混合文本/扫描页的逐页 OCR；本机实际 Poppler/Tesseract 固定英文扫描页已验收。扫描件仍可能处于 ocr_required、ocr_partial 或低置信度状态，空白和识别失败不会被直接判成可靠原文。面试应说明这些限制，结构化切块的五组开发探针已验证公式/表格条件回填及正确锚点，但不能把固定回归探针当成广泛识别准确率或高精度版面理解。

### Q20：知行的 HashEmbedding 是语义向量模型吗？

- **口述答案**：它是确定性的本地哈希特征，不具备训练过的语义理解能力。当前词法检索依赖查询扩展和排序；可选 Ollama 本地嵌入另行建立语义索引。不能因为存了向量就宣传为高质量语义检索。
- **知行具体怎么做**：HashEmbeddingModel 默认把词或汉字映射成六十四维带符号的哈希特征并归一化，没有训练学习语义。导入会存这些特征，但普通 DocumentLibrary.search 实际走 expandQuery 与 rankEvidence，要求词项命中，不让哈希碰撞建立相关性。可选 SemanticIndex 才调用本机 Ollama 的嵌入接口，另表保存向量及模型身份，不能把两条路径混说。
- **分析路径**：分别测试同义问法、无关词碰撞、多语言和长文档；检查真正使用的检索路径，而非只看类名。
- **Trade-off**：词法方案轻量、离线、可解释，但语义覆盖有限；真实嵌入改善语义匹配，同时增加本地模型依赖、资源消耗和版本管理。
- **追问**：项目是否已经部署云端向量数据库或交叉编码器？存了向量为什么不够？
- **追问答案**：没有这两项部署。当前语义向量保存在本地 SQLite，嵌入请求固定连接本机 Ollama；交叉编码器是同时读取问题和候选片段再打分的模型，项目未实现。向量只是一串数字，来源可能只是哈希特征；是否有语义检索收益，要看真实嵌入模型和有标注问题集上的表现。
- **源码与测试索引**：[HashEmbeddingModel](../../src/embedding.ts)、[词法排序](../../src/retrieval-query.ts)、[SemanticIndex](../../src/semantic-retrieval.ts)、[检索测试](../../tests/retrieval-quality.test.ts)、[检索入口](../../src/library.ts)。

### Q21：RRF 融合与 reranker 有什么区别？项目用了什么？

- **口述答案**：知行的 fuseEvidence 根据两个结果列表的排名贡献融合并去重，不比较不同检索器原始分数。它不是再训练一个模型判断“问题与文段是否相关”的交叉编码重排器。
- **知行具体怎么做**：fuseEvidence 依次遍历词法和语义两个列表，按从零开始的名次计算倒数贡献并相加，排序偏移量固定为 60；相同 chunkId 合成一个候选，最后取八条。这样某片段在两路都排名靠前就更容易留下，不要求两路分数同量纲。普通 rankEvidence 则按命中词和文本长度打分，两者都没有额外调用神经网络来重新理解问题与片段。
- **分析路径**：先提高候选召回，再决定融合和重排；比较 top-k 命中、噪声、延迟和输入成本。现有融合实现可以作为基线。
- **Trade-off**：排名融合简单且不需要分数校准；模型重排可能更精准，但增加推理开销和部署复杂度，收益需用资料集验证。
- **追问**：为什么不能把 rankEvidence 或 fuseEvidence 称为已经部署的神经网络 reranker？
- **追问答案**：因为它们执行确定性规则，没有加载或调用重排模型。rankEvidence 衡量词项匹配，fuseEvidence 合并已有名次；真正的模型重排还要读取问题与候选并生成新相关性分数。可以称当前实现为词法排序和排名融合，并把神经重排列为需要单独评估成本与收益的扩展。
- **源码与测试索引**：[fuseEvidence](../../src/semantic-retrieval.ts)、[rankEvidence](../../src/retrieval-query.ts)、[检索质量测试](../../tests/retrieval-quality.test.ts)。

### Q22：答案带引用，为什么仍然可能错误？

- **口述答案**：引用可定位只证明片段存在；答案可能误读原文、引用了不支持的数值或忽略条件。知行进一步检查引用来源、精确数值、引号与过强措辞，但明确不宣称这些规则证明语义蕴含。
- **知行具体怎么做**：answerFromEvidence 先拒绝无证据或缺少来源位置的输入，最多给模型前三条证据；返回后检查引用是否来自这批片段，再交给 inspectEvidenceSupport 检查紧邻数值、引号、过强措辞和来源歧义。例如有合法引用却把“可能减少等待”写成“保证降低 50%”，仍会被规则拦下。主助手路径也使用证据检查，但通过检查不等于推导已被证明。
- **分析路径**：把引用有效性、证据支持度、推导正确性和表达质量分开；无证据时保留不确定或拒绝来源限定回答。
- **Trade-off**：严格证据规则降低错误断言，也可能误伤合理推导；因此需要可解释错误与人工/模型复核，而不是一个“可信”总开关。
- **追问**：如果数字确实在引用片段里，为什么仍可能不支持答案中的指标或实验？
- **追问答案**：例如原文写“延迟降低 20%，成本降低 5%”，答案却声称“成本降低 20%”。数字存在但指标错配。现按子句分别匹配成本、延迟、命中率、准确率、召回率，区分 P50/P95、增减方向、降幅/降至以及显式前后值；“仅在……时/only when”条件未保留时要求重写，不能借用假设或尚未实测的数字。同时回归多指标正确答案、否定/小数和代码示例，降低误拦。隐含条件、任意改写、跨句推导仍需复核，规则不冒充通用语义判定器。
- **源码与测试索引**：[inspectEvidenceSupport](../../src/evidence-support.ts)、[answerFromEvidence](../../src/grounded-answer.ts)、[证据测试](../../tests/evidence-support.test.ts)、[指标条件与误拦回归](../../tests/evidence-support-boundaries.test.ts)、[引用回答测试](../../tests/grounded-answer.test.ts)、[主助手证据检查](../../src/assistant-runtime.ts)。

### Q23：如何评估 RAG，才能分清“没找到”与“答错了”？

- **口述答案**：建立带相关片段标注的问题集，先测检索是否覆盖必要证据，再在固定证据下测生成是否忠实，最后测端到端。另设无答案、跨主题、旧版本和注入案例。
- **知行具体怎么做**：retrieval-quality 测试先检查“缓存旧数据”能命中英文 stale，跨主题与无关问题返回空，还检查邻块补充与去重。grounded-answer 测试再固定证据，验证无证据、缺引用和伪造位置的处理；分层 benchmark-rag 再对八题分别运行固定正确证据生成与实际检索后生成，保留原始模型回答、输出检查和用户可见结果；评分项不发给生成器。曾在真实 Codex 对照中发现规则误拦 100→80 毫秒的合法差值/百分比，已用有限算术与相邻条件检查修复并复测。质量评测保存原题、条件、回答及待人工复核状态。另新增 30 题固定公开开发集和 benchmark-retrieval：经真实导入检索，分别评测词法、指定本地嵌入、融合三路，记录 Recall@3、Precision@3、MRR、nDCG、无相关资料误召回和范围违规；不可用、失败与词法回退单独计数。开发集成绩不代表未见资料或最终回答正确率。
- **分析路径**：记录正确片段是否进入候选和最终上下文；若已进入仍答错，优先分析提示、证据冲突和推理；若根本没进入，改切块和检索。
- **Trade-off**：细粒度标注成本高，但比只看最终“像不像对”更能定位改进。自动指标应与人工判定校准。
- **追问**：如果报告 recall@k，应怎样定义分母？返回八条结果能说明召回率高吗？
- **追问答案**：召回率看的是标注为相关的证据找回了多少，分母是该问题应找回的相关片段数，而不是返回条数。举例：题目需要四个片段，前五条只包含其中三个，召回率才是 75%。还需说明标注的是全部相关片段还是必要证据；新检索评测按每题标注的相关“文档＋锚点”作为分母，重复块只计首次命中；无相关来源的问题不生成虚假的满分召回率，改报误召回率。标注范围是公开开发手册，不是所有用户资料。

### Q24：资料更新、模型更新后，旧索引和旧验证还能用吗？

- **口述答案**：要匹配内容与模型版本。知行语义索引记录模型身份和内容哈希，实际 Ollama 模型摘要变化会被识别；项目证据也绑定实际内容哈希，实践作业的实现或测试脚本改变后，旧运行验证不能自动继续有效。
- **知行具体怎么做**：SemanticIndex 按片段 ID、模型身份和内容哈希判断复用；Ollama 身份包含本机模型 digest，请求前后都复核是否变化。资料引用用实际片段文字重算 contentHash，打开来源时可发现版本不符。另一个 EvidenceStore 管理实践作业证据：实现或测试脚本的哈希变化，会令旧运行验证失效。摘要另绑定生成规则与自身内容哈希，失配不再注入；文档提取/切块 recipe 控制重复导入与 OCR 复用，语义向量另有处理规则版本。语义构建和查询在异步返回后复核来源，防止等待期间变更导致使用旧结果。这些具体依赖链不等于所有历史结论自动重算；外部同名模型及 OCR 引擎内部版本仍有可观察性限制。
- **分析路径**：为每个派生产物写清依赖：原文、切块、嵌入模型、提示和代码。只复用依赖仍一致的结果。
- **Trade-off**：严格失效增加重建成本；宽松复用速度快，却可能给旧答案套上新证据。
- **追问**：模型名相同但权重摘要变了该怎么办？内容哈希通过能证明原文可靠或答案正确吗？
- **追问答案**：本地 Ollama 路径会把摘要变化当作模型身份变化，旧模型的向量不会继续匹配，应重新建立对应索引；请求中途变化则拒绝该结果。内容哈希只证明读到的文字与绑定版本一致，不能证明作者、事实或推导正确。远端同名模型若没有可见版本信息，也不能声称自动检测到了变化。
- **源码与测试索引**：[SemanticIndex](../../src/semantic-retrieval.ts)、[source-version](../../src/source-version.ts)、[EvidenceStore](../../src/evidence-store.ts)、[证据应用测试](../../tests/evidence-application.test.ts)、[来源版本测试](../../tests/evidence-support.test.ts)。

## 五、工具执行与故障恢复（25—30）

<a id="q25"></a>

### Q25：为什么要有统一 ToolHarness？

- **口述答案**：模型只能提出工具调用，ToolHarness 才执行输入校验、主题边界、风险上限、超时和结果限制。把这些规则放在每个 Prompt 或每个工具里容易产生不一致。
- **知行具体怎么做**：工具注册时声明输入 schema、risk、超时和幂等性；ToolHarness 从可执行 schema 生成给模型看的定义。执行时先检查允许列表、取消状态、原始 topicId 与当前风险上限，再解析参数、做业务校验并调用工具。返回内容超过 11,000 字符时做有界输出，能归档则给分页引用。模型提出写请求，不会因此自动获得 write 权限。
- **分析路径**：明确工具定义、运行上下文和结果契约；执行前校验，执行后限制输出；审计只暴露必要诊断信息。
- **Trade-off**：统一边界让扩展更可靠，但工具的业务幂等性与外部副作用仍需工具自身明确声明和实现。
- **追问**：工具名在白名单里，是不是参数一定合法，而且这次任务也拥有写权限？
- **追问答案**：不是。白名单只回答工具是否可被发现和调用；参数还要通过 schema 与业务规则，写权限还由本次执行上下文限制。例如 write 工具虽已注册，maxRisk 为 read 时仍会被拒绝。原始 topicId 指向别的主题也会提前拦截，不能依赖模型自觉遵守名字背后的约定。
- **源码与测试索引**：[ToolHarness](../../src/tool-harness.ts)、[ToolDispatcher](../../src/tool-dispatcher.ts)、[工具边界测试](../../tests/tool-harness.test.ts)、[工具契约测试](../../tests/tool-spec.test.ts)。

<a id="q26"></a>

### Q26：JSON Schema 或结构化输出能保证工具调用安全吗？

- **口述答案**：只能保证部分形状约束。合法字符串也可能指向越权路径，合法对象也可能请求不允许的操作；必须继续做业务语义和权限校验。远端 MCP Schema 的复杂度也需要约束。
- **知行具体怎么做**：ToolHarness 在 Zod 解析之前先检查模型传来的原始 topicId，因为对象 schema 可能剥离未知字段；随后 validatedPreview 执行业务验证和预览，正式 execute 再核对当前权限并复验。MCP 的远端 schema 交由限制内存和执行时间的 JsonSchemaWorker 处理，拒绝远程引用和不支持的方言。参数符合结构，仍必须经过路径政策与授权检查。
- **分析路径**：从协议校验到业务校验，再到授权、执行和结果验证分层；禁止以模型自报的 topicId 覆盖运行上下文。
- **Trade-off**：严格 schema 减少歧义，但不能替代执行时检查；宽松 schema 方便模型调用，却增加错误修复成本。
- **追问**：JSON 能解析与业务能执行有什么区别？为什么不能先让 Zod 剥离越权字段？
- **追问答案**：能解析只说明文本是合法 JSON，字段类型正确也不代表路径或操作被授权。如果先剥离模型提交的异主题 topicId，后续看到的干净对象就掩盖了原始越权请求。知行先检查原始参数的主题边界，再做结构解析；路径、风险和实际执行条件继续由受控运行时判断。
- **源码与测试索引**：[validatedPreview](../../src/tool-harness.ts)、[Schema 隔离 worker](../../src/json-schema-worker.ts)、[Schema 方言测试](../../tests/json-schema-dialects.test.ts)、[路径政策测试](../../tests/path-policy.test.ts)。

### Q27：工具报错应该抛异常、让模型重试，还是直接失败？

- **口述答案**：按类型处理。参数错误返回可修正的结构化信息；权限失败不能靠重试绕过；外部临时错误可以在明确预算内重试；副作用结果未知应进入恢复状态。不要把所有错误都化成一句“重试”。
- **知行具体怎么做**：普通工具失败返回包含 ok、errorCode、durationMs 的 ToolResult；Zod 错误最多暴露八个字段位置与类型提示，不返回原始值。未知异常统一收敛为 tool_failed，便于避免泄漏。已派发的非幂等写调用若超时或取消，则抛 ToolOutcomeUnknown，保留恢复边界；它不能作为普通失败交给模型重试。可修正输入通过续轮处理，仍受轮数与重复调用限制。
- **分析路径**：区分输入、业务、基础设施、取消和未知结果；给模型错误代码与字段位置，避免把凭据或原始敏感参数返回到上下文。
- **Trade-off**：详尽诊断便于自修复，也增加泄密和提示注入风险；白名单化错误可减少风险但要求维护错误目录。
- **追问**：MCP 协议错误和工具执行错误有什么区别？HTTP 成功就意味着业务成功吗？
- **追问答案**：协议错误是帧、版本、消息结构等通信契约无法正确处理；工具执行错误是请求到达工具后，业务处理未成功。MCP 即使完成一次传输，工具也可能返回 isError。知行会区分远端错误与结果未知的写操作，不能把 HTTP 状态或一句普通文本直接视为成功回执。恢复核验还拒绝 isError、错误身份和可选的原请求哈希错配；支持配置宿主生成的操作键并在断线恢复时复用，服务端真实去重仍需服务履行契约。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- **源码与测试索引**：[toolFailure](../../src/tool-harness.ts)、[公开错误](../../src/agent-errors.ts)、[工具调度测试](../../tests/tool-dispatcher.test.ts)、[MCP 工具测试](../../tests/mcp-tools.test.ts)、[MCP 调用结果边界](../../src/mcp-connection.ts)。

<a id="q28"></a>

### Q28：为什么“超时了，再执行一次”会造成严重问题？

- **口述答案**：超时只表示客户端没有拿到确定结果，外部写入可能已经发生。知行对已派发的非幂等写调用保留未知结果，要求核实或明确报告，不自动重放。
- **知行具体怎么做**：collectInvocation 在调用工具前将 pending 标记 executing 并保存，再派发动作。ToolHarness 对已派发、非只读且非幂等的超时调用抛出未知结果，恢复时先检查可重放声明。MCP 配有核验契约时，可按原操作标识执行只读查询；没有核验能力就保留未知或用户报告。这里的幂等是重复执行不增加额外效果，不能仅靠工具名字猜测。
- **分析路径**：先持久化执行意图，再派发；把未开始、执行中未知、已确认成功分开；恢复时优先查询外部状态或利用服务端幂等键。
- **Trade-off**：保守恢复降低自动化程度，但避免重复发消息、重复创建资源或重复扣费。服务端幂等支持能改善体验，但不是所有工具都有。
- **追问**：用户说“已经成功”能记成服务端核验吗？本地日志能保证跨服务恰好执行一次吗？
- **追问答案**：都不能。TaskContinuity 将用户描述记录为 source=user_report、verified=false，不伪造原工具成功回执。只有受信核验适配按操作身份查询服务并匹配状态，才记为外部核验。本地日志能保存意图与已知结果，但断网时仍存在确认缺口；跨服务只执行一次还依赖服务端幂等或事务契约。
- **源码与测试索引**：[ToolOutcomeUnknown](../../src/tool-harness.ts)、[TaskContinuity](../../src/task-continuity.ts)、[MCP 恢复](../../src/mcp-recovery.ts)、[恢复边界测试](../../tests/agent-recovery-boundaries.test.ts)、[执行意图保存](../../src/model-invocation.ts)、[未知写结果测试](../../tests/mcp-tools.test.ts)。

### Q29：取消一个 Agent 任务需要取消哪些东西？

- **口述答案**：包括排队等待、网络读取、模型进程、工具、成员任务、摘要维护和 UI 订阅的相关工作。取消之后不得再启动新副作用；已发生的写入不能因为取消而被抹掉。
- **知行具体怎么做**：AgentService.stop 会取消交互和后台摘要控制器，暂停当前会话队列，再中止活动请求；父级 AbortSignal 向模型和工具传播。原生进程宿主先发 SIGTERM，五百毫秒后仍未退出则发 SIGKILL，并对无法确认退出的情况报错。HTTP 读取和工具也需消费取消信号；未知写结果仍需核验才能恢复，取消不会删除既有回执或撤销外部副作用。
- **分析路径**：传播同一取消链，合成父级信号与局部超时，清理监听器和进程，再把状态持久化为 interrupted/cancelled 等真实结果。
- **Trade-off**：强制终止进程响应快，但无法自动回滚外部操作；协作式取消更容易清理，却要防工具不响应。
- **追问**：用 Promise.race 加一个超时，就能保证底层请求和工具已经停止吗？
- **追问答案**：不能，竞争只让外层较早返回，另一个 Promise 仍可能继续运行。知行除了等待超时，还向 fetch、流读取和原生进程传递取消或终止动作。对于不响应取消的任意工具，只能结束等待，不能凭此确认副作用未发生；因此非幂等写调用要进入结果未知的恢复流程。
- **源码与测试索引**：[AgentService.stop 相关逻辑](../../src/agent-service.ts)、[abortable](../../src/abortable.ts)、[原生进程宿主](../../src/native-agent.ts)、[生命周期测试](../../tests/agent-cli-lifecycle.test.ts)、[工具取消测试](../../tests/tool-harness.test.ts)、[原生宿主测试](../../tests/native-agent.test.ts)。

### Q30：哪些工具可以并行？怎样防止死循环？

- **口述答案**：只读不必然独立，只有显式声明纯读、幂等且 parallelSafe 的工具才可进入安全并行。LoopGuard 同时限制模型轮数和相同状态下重复工具调用，写入改变资源状态后应重新判断观察是否有效。
- **知行具体怎么做**：ToolHarness 只接受同时为 read、idempotent 且 parallelSafe 的并行声明；collectInvocation 每批最多执行两个符合条件的相邻调用，写操作和交互形成串行边界。LoopGuard 规范化对象键后检查重复调用，并结合已完成操作或同资源成功写入的状态。默认最多六轮、三十二次工具调用；项目工具场景可增加到十二轮，但仍有总时限和预算。
- **分析路径**：先确定共享资源和副作用，再安排并行；规范化参数用于重复检测，保留数组顺序，不能只比较字符串键顺序。
- **Trade-off**：更多并行降低墙钟时间，但增加竞争与错误传播；严格限制可能少用并发，却能保持执行语义。
- **追问**：外部状态变化后重复读取可能合理，知行怎样避免误判？它能感知所有外部变化吗？
- **追问答案**：防循环键包含资源状态，所以本任务记录到同资源成功写入后，相同参数的读取可以重新获得意义；数组顺序仍保留。现在还支持显式配置的外部版本观测：只接收结构化响应、精确资源身份和有效版本，并将回执保存在执行日志，防循环按当前查询资源匹配。正文变化不算版本，其他资源变化不解除本资源的重复限制。首次观测建立状态，后续同版本重复仍停止；真正查询到新版本才可重读。仍不会自动感知别的用户修改，不能称为通用外部变化订阅。

## 六、同模型与异模型团队（31—36）

<a id="q31"></a>

### Q31：单 Agent、同模型团队、异模型团队分别适合什么？

- **口述答案**：单 Agent 适合简单或强依赖任务；同模型团队便于在相同能力与协议下分工独立检查；异模型团队可能带来不同能力和错误模式，但增加协调、延迟与能力对齐成本。默认不应假设团队一定更好。
- **知行具体怎么做**：知行在 `teamConfigurationSchema` 中提供三种模式，默认单 Agent；团队配置只允许一至两名成员，默认分配推理核查与事实核查。同模型模式核对提供商、模型和连接是否一致，异模型模式要求至少两个不同模型 ID。协调器负责分工、成员报告、审查和综合，例如让一人核算、一人检查题设；分工独立只是执行职责分开，不代表错误互不相关。
- **分析路径**：先看可分解性和独立核验价值，再看单模型基线是否已经足够；同模型多次调用也不等于独立统计样本。
- **Trade-off**：同模型更易控变量但错误相关；异模型潜在多样性更高但并非天然互补。应按任务分层比较真实收益。
- **追问**：知行团队能让成员任意互聊、继续创建无限子 Agent 吗？
- **追问答案**：不能。成员走固定协调器调用，执行参数设为只读、禁止写入、清空写授权，并且不能继续委派；配置还限制人数、模型轮次、工具次数和总时限。依赖结果由协调器按任务关系传递。两个成员即使分工不同，仍可能共享模型偏差或同一份错误题设，需要核验依据。
- **源码与测试索引**：[团队配置](../../src/team-contracts.ts)、[协调器](../../src/team-coordinator.ts)、[历史对照](../evidence/team-resource-budget-20260911.md)。 [模式约束测试](../../tests/team-contracts.test.ts)、[成员工具隔离测试](../../tests/team-isolation.test.ts)。

<a id="q32"></a>

### Q32：为什么团队用 DAG，而不是简单 Promise.all？

- **口述答案**：有的任务依赖前一个结果，有的任务可独立执行。DAG 显式表达依赖，运行时拒绝循环和缺失依赖，并按可执行波次调度；同一成员的任务也不能冲突并行。
- **知行具体怎么做**：DAG 即“有方向、无环的依赖图”。`parseTaskPlan()` 接受一至四项初始任务，检查重复 ID、缺失依赖、成员覆盖和环；`runTaskGraph()` 每次选择依赖已完成且成员未被占用的任务，先保存 running 状态、新执行 ID 和尝试次数，再并行执行这一波。若先查资料再验算，验算必须等资料任务完成；前置失败则标记 blocked，而非照常综合。
- **分析路径**：规划时验证任务 ID、成员覆盖和依赖；派发前先存意图；失败后阻塞依赖任务；保存实际执行 ID 和尝试次数。
- **Trade-off**：DAG 更可追踪，但规划和验证增加开销。只有两个独立短核查时简单并行足够，不必制造复杂依赖。
- **追问**：任务图能一直重试，或者直接作为跨机器工作队列吗？
- **追问答案**：都不能。初始规划最多四项，每项最多三次执行尝试；后续复核也受总体任务、轮次与时间预算限制。本地调度只负责选出一波可执行任务，再用并行 Promise 等待结果。跨机器还需要共享队列、认领续期、故障转移和重复投递处理，当前没有这些部署能力。
- **源码与测试索引**：[parseTaskPlan / runTaskGraph](../../src/team-task-graph.ts)、[工作契约](../../src/team-work-contracts.ts)、[图测试](../../tests/team-task-graph.test.ts)。 [团队并发与预算边界](../../src/team-budget.ts)。

<a id="q33"></a>

### Q33：团队为什么可能比单 Agent 答得更差？

- **口述答案**：常见原因是错误分工、共享了不完整上下文、成员因预算截断、内部格式污染任务、错误多数票、综合阶段丢条件，以及额外调用引入故障。团队还可能重复同一个模型的偏差。
- **知行具体怎么做**：知行要求成员提交 summary、claims、basis 和 uncertainties，分别表示摘要、具体命题、依据及未决问题；主 Agent 再逐项审查，必要时定向追问后重新审查。历史 H02 中 DeepSeek 首轮序列错误，Codex 审查追加核查才得到正确最终结果，整题耗时 228.6 秒。这个例子说明报告能交付只是第一关，团队还可能为纠错增加时间，并非成员一多答案就更准。现有评测行另输出阶段诊断：规划、成员、审查、复核和回答的调用、格式问题、已知/未知用量；单列追加复核及再审成本、命题值变化和验收覆盖，仍不把结构完成当成语义正确。
- **分析路径**：分别检查规划、成员、审查、综合产物，定位最早错误；再做移除某阶段、扩大预算或统一上下文的消融，而非直接宣布模型不够强。
- **Trade-off**：多一层审查能发现部分错误，却也能引入新误判和延迟；应以可验证问题驱动定向复核。
- **追问**：H02 最终正确，能证明降低成员思考档位更聪明，或者每个成员都更准确吗？
- **追问答案**：不能。较低档位帮助成员在输出额度内交出报告，但历史报告仍有错误，是追加审查与复核纠正了它。预算档位影响可用计算和截断风险，不能直接当作智力变化；还要保留初答、纠正依据及额外调用，分别评价成员准确性和最终交付质量。

### Q34：主 Agent 说“大家都同意”，为什么不能判团队验收成功？

- **口述答案**：一致意见可能共同错误。知行按每项任务验收条件建立覆盖关系，审查需要引用具体任务及依据；区分 unresolved、model-reviewed 和 evidence-linked，不能把模型自评提升为工具实证。
- **知行具体怎么做**：`verifyTeam()` 遍历每项任务的 acceptance，也就是预先约定的交付条件，查找对应审查项。每个 supported 项必须指向已完成任务及真实命题；带 evidenceIds 时，还要关联任务中成功的工具回执。只有口头说 ready、没有逐项覆盖仍是 unresolved；全覆盖但只有模型推理是 model-reviewed，全覆盖且都有工具关联才是 evidence-linked。例如遗漏“检查边界条件”这一项，仍不能获得完整覆盖结论。
- **分析路径**：检查任务是否完成、验收条件是否逐项覆盖、证据 ID 是否属于本次执行且成功、是否仍有不确定项。
- **Trade-off**：细粒度覆盖比一个总分昂贵，但能暴露遗漏和伪造依据；仍然不能把结构覆盖等同于数学证明。
- **追问**：显示 evidence-linked 后，是否就不用再检查原证据与推导了？
- **追问答案**：仍要检查。该状态保证的是“验收项—命题—本次成功工具回执”关联齐全，不能证明原文真实、检索范围完整或计算解释没有错。例如工具正确返回一段资料，模型却把数字归给错误指标，仍需语义核对。测试也会拒绝伪造、失败、跨任务回执和遗留不确定项。
- **源码与测试索引**：[verifyTeam](../../src/team-verification.ts)、[团队证据测试](../../tests/team-verification.test.ts)、[工具证据测试](../../tests/team-tool-evidence.test.ts)。

### Q35：成员应该共享全部主 Agent 上下文吗？

- **口述答案**：不应默认共享。知行建立受控任务包，显式处理 shareContext；成员报告和原始材料视为数据，不能改变系统指令、授权或最终交付格式。成员保持只读且不能继续委派。
- **知行具体怎么做**：`buildTeamPacket()` 默认不共享历史；明确开启 shareContext 后，选取至多十二条历史，并优先保留显式目标、约束、纠正和未完成事项的原文锚点；历史与锚点合计不超过 24,000 字符。长消息保留首尾、Unicode 完整，跳过 system，记录省略条数/字符和源哈希；载入时也检查总预算及冻结包完整性。`packetMessages()` 把历史和锚点包装成“仅数据”的观察；规划、成员、定向复核、审查与最终综合均保留授权锚点，关闭共享时不附带它们。成员另外获得当前题目、验收条件、已完成依赖，以及本成员最近的公开报告；工具层同时限制只读，资料授权也不会因开启共享而自动产生。
- **分析路径**：按子任务传必要问题、条件、材料及依赖结果；不要复制主 Agent 私有历史和所有资料。审查同样只看规定输入。
- **Trade-off**：最小上下文减少泄露、污染和 token 成本，但可能漏掉重要条件；需要任务包完整性和缺失信息处理。
- **追问**：既然成员 Prompt 已写“只读”，为什么还要执行层限制？
- **追问答案**：Prompt 只是给模型的行为说明，模型可能误解或被资料指令影响。知行把 `readOnly: true`、`allowWrites: false`、空写授权传入 Runtime，并由 ToolHarness 同时限制工具发现和执行。测试故意在限制后新注册 MCP 写工具，仍会拒绝，所以安全边界不依赖模型自行守约。

### Q36：团队部分失败后怎样恢复，才不重复消耗所有成员？

- **口述答案**：保存规划、任务状态、执行 ID、已完成报告、资源预留和模型绑定；重启后运行中的任务标记中断，按明确的可重试条件定向恢复。已有成功报告保留，不能重跑后覆盖旧事实。
- **知行具体怎么做**：恢复时协调器比较 configHash、scopeHash 和原模型绑定，拒绝配置或授权范围已变化的旧任务。用户选择失败任务后，只把该任务重新排队，成功同伴的报告和旧执行记录保留；未派发过的阻塞后继可以继续。恢复测试验证新增调用依次只有 MEMBER、REVIEW、FINAL，旧失败 run 与新成功 run 同时存在，之前未知的用量也没有被清零。
- **分析路径**：验证配置和范围未变，再判断目标任务及其依赖能否继续；保留各次 run 记录，给新执行分配新 ID。
- **Trade-off**：定向恢复比全量重跑复杂，但降低费用并保留因果链；若上游条件确实变化，应新建任务而非勉强复用。
- **追问**：恢复为什么不能只把旧聊天记录发给模型，让它接着做？
- **追问答案**：旧聊天不包含完整的派发事实，无法可靠判断工具是否执行、额度是否已占用、授权是否撤回。知行按保存的任务状态、模型绑定、权限范围和累计预算恢复；结果未知的外部写操作仍需核实。否则一句“接着做”可能重复消耗、换到新模型，或在旧授权下再次写入。

### Q37：如何保证并行成员不会同时把预算花超？

- **口述答案**：发送前串行持久化预算预留，为分工、审查和最终回答保留额度；拿到权威用量后结算。用量未知保留预留，存储失败则禁止新请求，而不是继续请求后再补记。
- **知行具体怎么做**：`TeamBudget.mutate()` 用 Promise 链串行修改并保存预算：先为当前请求占位，同时给审查和主回答留额度，再真正派发。每请求有持久化预留记录，输入按“已报告 + 未知预留”相加；校验汇总 usage 后才结算对应请求，重复或小数回报拒绝，缺失保留。实测误差用于下一次预留，重启和旧格式保守核算；保存失败会阻止后续请求。连接槽位还限制同一 Pi 连接一次只跑一个请求。原生执行器仅做返回后用量核算，可能超过输出目标，因此不能承诺所有通道都有硬 token 上限。
- **分析路径**：检查预留操作是否原子串行、取消是否发生在派发前、重复 usage 是否重复结算、失败是否丢失未知消费。
- **Trade-off**：保守预留降低预算利用率，但避免把网络失败当零成本。原生 CLI 没有硬 token 限额，只能报告观察性质并用时间、字符和次数限制。
- **追问**：能把团队输出 token 相加，当作实际花费金额吗？
- **追问答案**：不能。token 是文本计量单位，金额还取决于提供商、模型、输入与输出单价、缓存优惠和订阅规则。知行记录用量与 unknownUsageRequests；缺失回执不能写零，原生订阅调用也不能直接按 API 价估算。若要展示金额，应另建有日期和版本的价格表，并明确估算范围。

### Q38：如何定位“连接模型很慢”？

- **口述答案**：拆分模型选择、进程启动、认证准备、请求等待、首事件、首正文、生成完成和退出清理。再区分网络路径、模型推理、工具等待和本地渲染，不能只看一个总秒数。
- **知行具体怎么做**：知行的 `ModelTiming` 将客户端耗时分为模型选择、worker 启动、请求等待、首事件、首正文和进程收尾。首事件可能只是协议消息，未必已有可展示文字；requestMs 又包含认证准备、网络与远端处理，不能进一步冒充服务端纯推理耗时。Pi 延迟测试使用合成 SDK 核对事件和退出顺序，连接验收则另存真实短题及失败记录。另有共享新实例/复用实例基准、失败率与分位数；2026-09-18 官方 Codex 四次公开短题首正文 6.02–8.20 秒、总时长 9.81–15.80 秒。每组两次不足以宣称稳定性能提升，原生完整消息口径单列。
- **分析路径**：用固定最小题复测直接与指定代理路径，记录成功和失败；将进程事件与可见文本分开。原生首次完整消息不能冒充流式首 token。
- **Trade-off**：细分观测有助定位，但只能描述客户端看得到的阶段；过度推断服务端原因会误导优化。
- **追问**：三家各跑一次固定短题，能据耗时给模型整体速度排名吗？
- **追问答案**：不能。一次观测会混入启动、认证、代理、网络、回答长度与随机波动，只能证明该条件下这次调用的表现。可靠比较应固定题集和模型档位，多次重复并报告失败和分位数；原生 CLI 的首次完整输出也要单列，不能同流式首正文时间直接混排。

### Q39：流式 UI 为什么不能每个 token 都全量刷新会话？

- **口述答案**：频繁全量更新会增加 IPC、序列化和渲染成本。知行发送带序号的消息补丁并在渲染端合并 delta，结束时确保最终文本刷新；订阅者断开不能反过来控制任务是否完成。
- **知行具体怎么做**：`AgentService` 分别发文本 delta（增量片段）和带递增序号的 message_patch（消息字段更新）；React 端用 `DeltaBatcher` 按会话、消息暂存文本，默认约 32 毫秒合并一次。新权威快照会丢弃已被覆盖的积压片段，任务 settled 时立即 flush。订阅回调异常只移除订阅者，不阻止后台完成；测试用一千个片段核对合并、尾段与计时器清理。
- **分析路径**：测每秒事件数、主线程阻塞、累计文本复制与最后一段丢失；处理切会话、旧快照覆盖和取消清理。
- **Trade-off**：批处理减少开销但略增显示延迟；窗口要小且结束时强制 flush。不能为了平滑动画延迟真正停止。
- **追问**：改成高频轮询整个应用状态，就能解决断线恢复吗？
- **追问答案**：不能。实时流负责及时显示，恢复读取负责重新取得已经保存的权威状态，两者职责不同。高频全量轮询仍会增加序列化和渲染负担，还可能把旧快照覆盖到新文本。知行保留持久会话并处理补丁序号和最终刷新，但这些机制不等于分布式断线重放协议。
- **源码与测试索引**：[AgentService.patch / emit](../../src/agent-service.ts)、[delta-batcher](../../desktop/renderer/delta-batcher.ts)、[批处理测试](../../tests/stream-batcher.test.ts)。 [渲染端事件合并](../../desktop/renderer/index.tsx)。

### Q40：Prompt cache、应用缓存、语义索引缓存如何区分？

- **口述答案**：模型服务的输入缓存复用计算；应用缓存复用配置或本地查询结果；语义索引缓存复用特定模型与文本的向量。它们的命中条件和隐私边界不同，不能统一叫“记忆命中”。
- **知行具体怎么做**：知行每轮通过 `LearningContextBuilder` 重新读取画像、相关记忆和教学状态，避免把已撤回内容封在旧 Prompt 中。`SemanticIndex` 则在 SQLite 保存片段向量，只有片段 ID、模型标识、内容哈希以及文档/语义处理 recipe 匹配才复用；MCP 目录还另有配置版本与时效校验。供应商回报的 cacheReadTokens 属于模型调用用量，和这些本地缓存分别记录；当前没有通用跨请求答案缓存。
- **分析路径**：定义缓存键包含什么版本、什么时候失效、是否跨权限范围；授权撤回后的上下文不能继续来自旧缓存。
- **Trade-off**：缓存提高速度，但过粗键会串会话、串模型或泄露已撤权内容。先做有来源的局部缓存，别缓存整个可变 Prompt。
- **追问**：供应商返回 cacheReadTokens，能说这是知行的答案缓存命中率吗？
- **追问答案**：不能。这个字段描述供应商报告的缓存输入 token 数，既不是返回答案的次数，也不是知行本地索引命中次数。若计算命中比例，还要明确分母及提供商字段含义。知行的语义索引复用看模型和内容哈希，学习上下文则逐轮重建，不能把三者合并称为“记忆命中”。
- **源码与测试索引**：[学习上下文逐轮重建](../../src/learning-context.ts)、[语义索引键](../../src/semantic-retrieval.ts)、[缓存用量口径](../../src/model-capabilities.ts)、[统一撤权测试](../../tests/unified-agent-policy.test.ts)。 [MCP 目录缓存](../../src/lazy-mcp.ts)。

### Q41：如果增加自动重试，怎样避免雪崩与超时失控？

- **口述答案**：先判断是否可重试与是否可能已有副作用；所有尝试共享总截止时间和预算，采用有上限的退避与并发控制，不能每次重试重新获得完整预算。知行三种 API 协议现共用有界 HTTP 重试器；流已经开始或结果未知时不自动重放。
- **知行具体怎么做**：当前 `ProtocolModelClient` 把调用方取消信号与单次超时合并，并把信号交给 fetch 和流读取；失败时仍保留已经收到的用量。团队另用共享预算及连接槽位约束新请求，单个失败任务也有显式重试上限。`abortable()` 负责及时停止等待，不能让任意底层操作自动撤销。fetchModelResponse 最多尝试三次，处理 429 或带 Retry-After 的 503，采用指数退避和随机等待，并尊重服务端最早重试时间；过长等待或总期限不足则停止。requestAttempts 和 retryWaitMs 记录额外成本。
- **分析路径**：区分限流、认证、永久参数错误、断流和未知结果；测试取消能终止退避等待，恢复不会重复收费性工作。
- **Trade-off**：重试提高短暂故障成功率，也可能放大流量、费用和延迟；低成本只读操作与外部写操作应采用不同政策。
- **追问**：知行现在是否已有统一退避重试器或服务商级熔断集群？
- **追问答案**：已有跨 API 协议的统一有限重试，尚无服务商级分布式熔断集群。三协议、取消、总期限、Retry-After、永久错误与用量不重复累计均有回归；原生订阅执行不套用 HTTP 重试策略，未知外部写入仍先核实。

### Q42：如何证明一次性能优化有效？

- **口述答案**：固定任务、模型版本、档位、预算和测量口径，保留冷启动与热运行、成功与失败，报告分位数和资源消耗，并确保质量不下降。单次变快只能作为线索。
- **知行具体怎么做**：桌面诊断通过 `summarizePerformance()` 按模型、实际思考档位、上下文规模和调用轮数分组，避免把不同任务混成一个平均耗时；测试专门验证这些条件会分开。历史预算实验同时保存请求、用量、耗时、失败和最终解释：H02 虽修复未完成，却耗时 228.6 秒。因此当前证据支持特定案例交付改善，不能改写为已证明稳定加速。
- **分析路径**：先建立阶段基线，找到关键路径，再做单因素实验；若同时改代理和思考档位，应如实说明无法把收益唯一归因于一项改动。

- **追问**：团队墙钟时间为什么既不等于成员耗时相加，也不总是最长成员耗时？
- **追问答案**：墙钟时间就是用户从开始到结束实际等待的时间。若两个独立成员同波并行，这一波主要等待较慢者；若后续任务依赖前者，就要等多个波次，再加分工、审查、综合与连接排队。知行同成员任务不能并行，Pi 连接还会串行，所以应沿真实依赖路径计时。

## 八、存储、桌面与安全（43—48）

### Q43：为什么项目同时有 SQLite 和 JSON，而不是统一一种存储？

- **口述答案**：SQLite 承担结构化学习数据、执行状态和事务；会话 JSON 便于独立保存、迁移与分段。各有职责，但跨两种存储不存在天然全局事务，需要恢复逻辑处理边界。
- **知行具体怎么做**：`ZhixingDatabase` 用 SQLite 保存资料片段、长期记忆和执行检查点，启用外键与 WAL 日志模式；结构化查询和同库事务在这里完成。`AgentSessionStore` 则把会话写为 JSON，长历史按 250 条分段，先写临时文件再重命名。执行事实应读检查点，UI 历史读会话；两处写入之间若崩溃，必须通过恢复逻辑核对，不能假设它们天然一起提交。
- **分析路径**：按查询模式、事务要求、迁移和备份设计存储；避免把 UI 文本当执行事实来源。
- **Trade-off**：多存储降低单一模型的复杂度，却增加一致性与备份要求；全部进数据库便于事务，但迁移和长文本组织也要设计。
- **追问**：SQLite 事务提交成功，是否意味着会话文件和外部工具效果也一起原子提交？
- **追问答案**：不是。原子提交指事务内数据库修改要么整体生效、要么整体不生效，其保护范围是该数据库事务。会话 JSON 重命名、MCP 服务写入各有独立边界；数据库回滚不会撤回外部已发生的操作。知行因此保存派发阶段与回执，跨存储失败时依据事实恢复，而不依靠单库事务兜底。
- **源码与测试索引**：[数据库](../../src/database.ts)、[会话存储](../../src/agent-session-store.ts)、[执行存储](../../src/agent-execution-store.ts)、[存储测试](../../tests/desktop-storage.test.ts)。 [SQLite 原子提交说明](https://sqlite.org/atomiccommit.html)。

### Q44：进程在工具执行中崩溃，如何知道下一步该做什么？

- **口述答案**：依靠持久检查点和事件，而非模型记忆。检查点保存已完成轮次、当前调用、派发阶段和消费；恢复先确认是否有未知外部效果，再决定可重放读取、继续生成或等待核实。
- **知行具体怎么做**：`AgentExecutionStore` 将轮次历史、待执行调用、next 游标和派发阶段写入检查点，并用本地 PID 与随机认领标识限制同时恢复。next 表示下一条待处理调用：停在 ready 与停在 executing 的含义不同，后者可能已产生效果。`TaskContinuity` 将用户自报单独记成未核验观察；即使用户说成功，也不伪造成原工具成功回执。
- **分析路径**：在派发前后、写结果前后、最终验证时注入崩溃，检查系统不会重复副作用或错误标完成；并防两个本地进程同时认领同一执行。
- **Trade-off**：更多检查点提高恢复精度，但增加写入次数和状态复杂度；应把不可恢复边界优先覆盖。
- **追问**：本地进程认领可以直接当作分布式租约算法吗？fencing 又是什么？
- **追问答案**：不能。本地 PID 存活检查依赖同一台机器；跨机器时会遇到网络分区和旧执行者迟到。分布式租约还要处理过期与续期，fencing 指用递增凭证让存储端拒绝过期执行者继续写入。知行当前只有本地认领及凭证匹配检查，没有跨节点续期、选主和隔离保证。
- **源码与测试索引**：[AgentExecutionStore](../../src/agent-execution-store.ts)、[连续任务](../../src/task-continuity.ts)、[崩溃测试](../../tests/agent-crash.test.ts)、[检查点测试](../../tests/agent-checkpoint.test.ts)。

### Q45：备份成功意味着恢复后可以直接继续所有任务吗？

- **口述答案**：不意味着。恢复需验证文件、数据库与引用完整性，处理工作区和会话身份映射，并保留不确定执行状态。密钥与授权不能随着普通备份随意传播。
- **知行具体怎么做**：完整工作区备份生成目录及 manifest 清单，逐项记录路径、字节数和 SHA-256，并创建一致的 SQLite 快照；恢复先校验清单和数据库，再创建新工作区。桌面会话 ID 重映射，运行消息改为 interrupted，执行、上下文、写入和 MCP 授权清空，队列暂停。学习试验保留原记录身份，因而恢复副本不会自动变成新样本；恢复成功后仍需用户重新核对任务条件。
- **分析路径**：做完整恢复演练，而非只检查备份目录生成；再测试旧版本、损坏文件、重复导入和运行中快照的限制。
- **Trade-off**：完整快照恢复方便，但体积大且可能包含私有资料；选择性导出更可控，却需要明确缺失哪些依赖。
- **追问**：为什么恢复副本不能算新教学样本，也不能继承已经撤销的授权？
- **追问答案**：副本重复的是同一次作答，合并时按试验 ID 去重，只保留合法更新，不把导出次数当学习者人数。授权则属于当前用户对当前范围的决定，不能从旧快照复活；知行恢复会清空相关授权和待发队列状态。即使原任务曾获许可，也要重新核对模型、资料范围与未知外部效果。

### Q46：Electron 应用如何防止渲染内容获得本机权限？

- **口述答案**：知行开启 contextIsolation 和 sandbox，关闭 nodeIntegration；preload 只暴露有限命令，主进程继续校验命令和发送方，不能因为 UI 看起来可信就放过 IPC。
- **知行具体怎么做**：Electron 窗口开启 contextIsolation、sandbox，关闭 nodeIntegration；preload 只把约定的命令桥接给页面。主进程接收 `zhixing:command` 时，先确认发送方就是当前窗口的主 frame，URL 也属于应用，再用 `desktopCommandSchema.parse()` 校验运行时对象。新窗口和主动导航被阻止。契约测试还检查超长消息与未知 provider，静态类型不会代替这些实际校验。这里的 IPC 就是页面与主进程之间的消息通信。
- **分析路径**：检查窗口配置、导航限制、IPC 入口、参数 schema 和敏感能力去向；模型 Markdown 与引用均视为不可信内容。
- **Trade-off**：限制桥接能力增加接口设计工作，但避免渲染漏洞直接扩大成本机任意操作。[Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security)
- **追问**：页面代码已经用 TypeScript 编译，为什么主进程还要验证 IPC 输入？
- **追问答案**：TypeScript 主要在编译时检查开发者写的代码，运行时传来的对象仍可能伪造或来自受攻击页面。主进程拥有文件与密钥能力，必须自己校验发送方、命令类型、字段和长度，再进入权限流程。知行的 Zod 契约会拒绝非法输入；共享内核依赖检查属于另一层，不能冒充 IPC 安全测试。

### Q47：API Key 存系统安全存储，为何还要关心签名和重复授权？

- **口述答案**：操作系统可能按应用身份限制密钥访问；开发构建身份变化会影响信任。知行桌面用加密安全存储，保留旧钥匙串兼容读取，并有固定本地签名流程；不把 Key 放进公开连接配置或模型上下文。
- **知行具体怎么做**：`EncryptedDesktopSecrets.status()` 只检查配置是否存在，旧钥匙串路径也只查元数据，连接时才 `get()` 解密；这样刷新设置不会反复读取实际密钥。新配置经主进程的 Electron safeStorage 加密后保存，安全存储不可用则报错，Linux 现在有条件支持已识别的同步 GNOME/KWallet 后端，拒绝 basic_text 和未知后端；不能拿同步后端名称替异步回退作保证。macOS 打包固定本地证书身份并校验签名要求，但历史跨构建检查不能推出所有系统永久免授权。
- **分析路径**：分清“Key 是否存在”的元数据检查和“实际解密/读取”，再核实应用签名、安装路径与迁移链路，避免把每次状态刷新都变成密钥读取。
- **Trade-off**：强系统保护可能带来授权交互；稳定身份和最小读取可以改善体验，但不能保证绕过所有系统提示。
- **追问**：本地签名、Developer ID 与公证是一回事吗？能因此宣称所有平台安全存储都验收了吗？
- **追问答案**：不是。本地签名用于固定本机开发应用身份，正式发行还涉及相应开发者证书、公证和发行验证。已新增 formal/preview 门禁，正式发行需要精确实包的七组 UI、原生存储、平台签名/公证及安装产物哈希。安全存储又取决于操作系统与实际构建；合成加密测试证明流程，真实系统测试才覆盖具体平台。2026-09-18 本机隔离原生存储探针初始化超时，正式门禁正确拒绝；Windows/Linux 原生流程待目标系统运行。知行保留 macOS 历史验收，不能把它扩大成 Windows/Linux 等价通过或永不弹窗。

### Q48：MCP 接入了可信服务，为什么仍要校验描述、输入和权限？

- **口述答案**：MCP 是工具通信协议，不自动提供宿主授权和内容可信保证。工具描述与返回内容可能含有注入，工具声明的风险也不是宿主权限依据；宿主仍应限制 schema、网络、进程、路径和结果。
- **知行具体怎么做**：知行按当前主题的 `McpSettings` 选择工具并确定风险、是否允许重放；目录缓存只用于发现，执行前会重新连接核对工具 schema 和配置版本。`ToolHarness` 再检查授权，服务不可用时只提供连接状态。对本地进程可选择 restricted 隔离；当前该 MCP 路径在 macOS 可用，其他平台拒绝启用。即使远端描述声称只读，也不能越过宿主配置与执行限制。
- **分析路径**：把发现、展示、用户授权、执行与结果使用分开；新发现工具也必须受既有单调限制，不能通过重新发现绕过策略。
- **Trade-off**：丰富工具提高能力，也扩大攻击面与上下文负担；按需发现、最小权限和可审计结果优于一次暴露所有工具。
- **追问**：可信服务自报“只读”就安全吗？Prompt 的拒绝规则能代替操作系统沙箱吗？
- **追问答案**：都不能。服务描述是外部输入，查询工具也可能偷读文件、外连或暗中写入；Prompt 只约束模型意图，不能阻止进程系统调用。知行分别以宿主权限和可用的系统隔离控制这些边界，测试用标成 read 的恶意服务尝试文件与网络越界，检查真实拒绝结果。

### Q50：怎样公平比较团队与单 Agent？

- **口述答案**：固定题目、模型身份、资料、评分和失败口径；同时报告默认产品配置与相近计算预算两类对照。加入单模型自检基线，避免把多花几倍调用的收益全部归因于团队。
- **知行具体怎么做**：`evaluateTeams()` 用同一份冻结 question 分别调用单 Agent、自检和同/异模型团队，预期答案保留在本地评分端，不发送给模型。每个结果保留 caseId、repeat、arm（实验组）、模型绑定、请求、耗时、用量和失败；运行顺序按题号及重复轮次轮换。自检组多轮重新检查原题，用来区分“多花调用”的收益与团队分工本身的收益，但不能据此声称严格等算力。
- **分析路径**：记录分工、实际档位、请求数、token、耗时、截断与失败；盲化候选顺序；不得只挑成功结果。
- **Trade-off**：相同次数不等于相同成本，相同 token 也不等于相同推理能力；应报告多个资源维度，而非宣称绝对公平。
- **追问**：同一道题在四种模式各运行一次，为什么不是四个独立题目？
- **追问答案**：因为题目内容、难度和陷阱都相同，四次结果是同一题的配对对照，相关性不能忽略。它能展示各模式在这道题上的差异，却不能扩成四道题的覆盖率。知行分别保留 caseId、repeat 和 arm；应增加不同题目并重复运行，按题比较正确性，再同时报告请求数和资源消耗。

### Q51：历史结果从 18/20 到 20/20，可以在简历上写“准确率提升 10%”吗？

- **口述答案**：不宜。这里是四道冻结题在不同组的运行总数，且成功口径包含完成、答案字段正确和有解释；不是 20 道独立题。更合适说“修复特定预算截断案例，有限回归由 18/20 改善到 20/20”，并附实验限制。
- **知行具体怎么做**：历史预算记录只覆盖 D01、D02、H02、H04 四道题，不同组相加形成二十次运行；旧轮十八次、新轮二十次满足“完成、答案字段正确、有解释”。`scoreTeamAnswer()` 检查字段预期值，而 explanationPresent 只检查解释字符串达到最小长度，并不理解语义。后续逐条解释复核仍指出 D01 单 Kimi 的位值措辞、D02 单 DeepSeek 的平方条件表述问题。
- **分析路径**：核实分母、独立样本、版本、网络和随机变化；区分百分点、相对比例与统计显著性；更多独立题与重复运行后再估计稳定收益。
- **Trade-off**：小实验便宜、能发现回归，却不能支持总体胜率或教学因果结论。
- **追问**：既然 20/20 都有解释，为什么还要说有两处教学措辞问题？
- **追问答案**：“有解释”只证明解释字段存在且达到长度要求，不保证每一句清楚正确。D01 应说明已包含十位权重的数值要按相同数位相加，避免再次移位；D02 应保留非负条件再讨论平方的等价性。这两处不改最终字段结果，但会误导初学者，须与机器字段评分分开报告。

### Q52：LLM-as-a-judge 怎样避免自夸、顺序和长度偏差？

- **口述答案**：先给明确 rubric 和可核验参考，再对候选匿名、随机顺序、限制无关冗长影响，并与人工标注校准。可客观计算的答案字段优先用确定性检查；评审模型不能因与自己相似就判优。
- **知行具体怎么做**：知行有两条不同评阅链路。团队内部用结构化报告和逐项 checks 做开发质量控制；学习者解释则由 `createBlindReviewPacket()` 生成匿名随机 ID、打乱顺序的评阅包，隐藏模型、实验组、阶段、自动分数和已有评分，负责人另持映射与原文哈希。当前还支持 Agent 回答匿名包、哈希绑定评分导入、两评阅者逐维一致性和按组方向偏差检查；学习者解释可批量导入到新导出文件，保留原评分历史。校准只比较指定参考，不自动认证评阅者。包本身不会自动产生评分或证明评阅者独立，原文中的自我披露仍需分享前检查。
- **分析路径**：测交换顺序是否变分、不同评审是否一致、错误解释是否高分；保留评语与证据，隔离题目中试图操纵评审的指令。
- **Trade-off**：模型评审扩展性好，但有相关偏差；人工成本高，也需要规范。知行当前开发侧解释复核不能说成独立人类盲评。
- **追问**：学习者解释盲评已经存在，能把团队历史解释复核也说成独立人类盲评吗？
- **追问答案**：不能。历史团队二十份解释由开发侧 Codex 复核，属于模型辅助质量检查；学习者盲评工具只是准备另一套待实际评阅的数据。前者不能冒用后者的匿名与独立性，后者也不意味着已有真实评阅者。rubric 即评分标准，应记录具体依据，并把自动字段分、模型复核和真实人评分别呈现。当前 explanation-v1 已分别评分正确性、完整性、清晰度，要求来源摘录；团队五阶段可导出，旧版评价仍标为维度未评分。新增 X01–X12 是已公开开发题，按题配对统计不把重复运行当独立题目；2026-09-18 真实三模型扩展对照因 Kimi 预检超时尚未开始。

### Q53：真实失败案例如何变成回归测试，且不“教会模型考试”？

- **口述答案**：先保留原始失败输入、轨迹、环境和版本，提炼确定性的协议或状态错误，再添加测试；模型行为部分采用训练/开发集与保留集分离，避免不停用同题调 Prompt 后宣称泛化提升。
- **知行具体怎么做**：团队用例把 question 与 expected 分开，实际请求不带参考答案，评分在本地完成；开发题和保留题也有明确集合。Agent 质量测试则用合成模型返回和主题资料，复现引用、工具续轮与越权边界。预算失败保留原始运行、用量和最终解释，不删除坏结果。已用于定位和调整预算的 H02 后续只能算回归题，不能继续包装成从未接触的新保留题。
- **分析路径**：分别建立解析、执行、答案和质量回归；评分规则冻结，修改评分器必须说明为什么，不许为当前输出降低要求。
- **Trade-off**：固定题便于比较，但易过拟合；新题提升外部有效性，却增加标注和运行成本。
- **追问**：同时改 Prompt、预算和评分器后结果更好，怎样知道是哪一项有效？
- **追问答案**：单看这一轮无法知道。应固定题目、模型、网络和评分规则，分别只改一项，再做去掉某项的消融对照；消融就是检查某个组件缺席时结果怎样。若只能整体修改，就如实报告组合改动及归因限制，保留原评分和失败，再用未用于调参的新题检查能否推广。

### Q54：Agent 的故障注入应该优先覆盖哪里？

2026-09-18 补充：新增[实际故障矩阵](../recovery-fault-matrix.md)，覆盖结算保存失败、SQLite 双写回滚、目标日志保护、恢复副本错换/损坏、最终替换失败及跨存储取消。新账目/摘要规则写 v14，防止旧格式静默丢掉预算语义。

- **口述答案**：优先覆盖不可逆或可能重复的边界：工具派发前后、预算预留后、结果落盘前、进程中断、取消与最终验证竞争、权限撤回和旧版本恢复。
- **知行具体怎么做**：`agent-recovery-boundaries` 测试把故障放在派发状态 ready/executing、恢复预算检查和最终完成检查附近，断言下一次工具是否真的执行、已返回结果是否仍在检查点，以及取消后不能记录完成。另一个用例让工具故意返回看似“未开始”的错误对象，重启后仍按真实已派发处理，防止返回文本篡改执行事实。团队测试还覆盖预留后存储失败和中断成员恢复。
- **分析路径**：每个注入点都断言最终状态、是否新增副作用、预算是否保留、是否能确定性恢复，而非只断言抛了异常。
- **Trade-off**：故障矩阵复杂，但比单纯提高文本断言数量更能提高可靠性；可按副作用风险排序覆盖。
- **追问**：工具返回 cancelled、not_started 等字样，运行时可以直接当作取消元数据吗？
- **追问答案**：不能。工具返回值是业务数据，工具可能出错或伪造标签；是否派发应由执行层在调用前后记录。知行即使收到伪装成 not_started 的结果，仍保留已派发事实并恢复防循环约束；取消后的外部写结果若未知，也不能把一句 cancelled 当作未发生副作用的证明。

## 十、教学差异化与生产演进（55—60）

<a id="q55"></a>

### Q55：已有成熟通用 Agent，为什么还做知行？

- **口述答案**：通用 Agent 提供执行和推理能力，知行的差异在资料驱动学习、实际作答记录、按证据给教学建议、实践项目与延迟保持验证。价值应由用户是否学会和能迁移证明，而非更长的回答。
- **知行具体怎么做**：知行把当前资料检索、实际知识检查、作答反思与帮助方式连成学习流程。`LearningObservations` 保存真实提交，`TeachingPolicy` 依据对应知识点建议正反例、引导练习或迁移练习，并优先服从用户“直接回答”“只给提示”等要求。`PracticeProjects` 将练习代码、测试和当前文件树绑定，效果模块再支持前后测及延迟测；代码跑通仍不能直接判定用户掌握。
- **分析路径**：把用户结果拆成理解、独立完成、迁移与保持；模型和执行内核尽量通用，教学业务保持清晰。
- **Trade-off**：领域约束降低通用性，但能形成可测闭环；若没有真实效果证据，就只能说提供了验证能力，不能说效果领先。
- **追问**：复用或对齐通用 Agent 内核，是否意味着知行的产品定位就是编程代理？
- **追问答案**：不是。共享内核提供模型调用、工具执行、权限和恢复；这些基础能力可以服务多种产品。知行在其上组织资料学习、实际作答、练习与保持验证，编程实践只是学习载体之一。当前能够展示这个验证流程，是否比通用 Agent 更有教学价值，仍要靠真实学习者及独立评价。

### Q56：模型判断“用户已经掌握”可以直接写入学习状态吗？

- **口述答案**：不能。知行区分用户命令、模型提议与分类，并要求相应确认或用户证据；教学策略依据真实作答及帮助方式给建议，不把一次答对升级为整体掌握。
- **知行具体怎么做**：`authorizeConversationTransition()` 区分用户命令、模型提议和模型分类；需要用户证据却没有证据时直接拒绝，模型触发的状态修改也不能跳过确认。`LearningObservations.capture()` 必须读取已经提交的知识检查结果，保存原始反思、帮助方式与知识点结果，后续更正留修订。`TeachingPolicy` 只给建议，例如独立答对后推荐迁移题，不写“已掌握”或自动完成课程。
- **分析路径**：追踪事实来源、是否独立作答、是否被提示、是否后来纠正；保留撤回和更正机制。
- **Trade-off**：显式证据比模型自动画像繁琐，但更少误判和长期污染；可用轻量交互收集证据，不能省略证据标准。
- **追问**：模型自己出题、自己作答，再说用户掌握了，为什么不算学习证据？
- **追问答案**：因为发生行为的是模型，用户并未独立选择、解释或完成任务，无法从模型表现推导用户能力。知行只从已提交的知识检查捕获观察，并区分独立、提示、看答案和未知帮助；即使真实用户一次答对，也仅是这次题目的证据，还需新情境与延迟检查来评估迁移和保持。

### Q57：知行怎样测“学会了”，而不是“答案生成得好”？

- **口述答案**：现有流程包含前测、学习、后测和三天后延迟测，使用不同题卷次序，记录是否独立作答、模型条件、课堂证据与构建来源；解释需要独立复核，未完成或条件变化的数据保留并标记。
- **知行具体怎么做**：`LearningOutcomeStore` 开始试验时打乱三套题卷顺序，当前阶段整张题卷（三题）及选项一次返回并显示；未完成时不暴露正确答案及未来阶段题卷。状态按 pre→lesson→post→waiting→delayed 推进；完成真实教学对话后才能进入后测，后测再等待三天开放延迟测。每阶段保存选择、解释、是否借助帮助和用时，模型条件与构建来源随课堂记录保存，解释初始标为待人工复核。现在另有新情境迁移作答与单独复核、评阅者来源/独立性声明，以及构建、实际课堂、72 小时延迟、两位独立人评等就绪检查；声明不等于身份或真实研究已核验。
- **分析路径**：先看前测基线与后测变化，再看延迟保持和迁移；区分 prompt_only 与 full_product，避免把提示方式试验称为完整产品验证。
- **Trade-off**：延迟测更贴近保持效果，但有流失与日程成本；短期满意度容易收集，却不能替代学习结果。
- **追问**：题卷顺序随机，是否代表参与者已随机分组，能够证明教学因果收益？
- **追问答案**：不是。普通个人流程仍是题卷顺序随机、学习方式自选，记录 learner_selected。新增研究流程单独冻结匿名名单、构建/模型条件、主要指标和缺失政策，用随机分配票据绑定参与者；全体已分组者进入意向性分母，报告失访与最差/最好界，受帮助或改条件者不静默排除。这只是研究工程能力：仍需真实招募、独立评阅和实际三天随访，不能因生成了随机票据就宣称因果收益。

### Q58：自选使用知行的人后测更高，为什么仍不能证明产品有效？

- **口述答案**：用户可能本来更有动力、基础不同、学习更久或看过相同题；自选分组存在混杂。当前汇总明确是描述性结果，排除重复、辅助作答和条件变化也不能消除所有偏差。
- **知行具体怎么做**：`summarizeOutcomes()` 把结论固定为 descriptive_only，即“描述性观察”；按模型与教学条件分组，标出重复练习、辅助作答、演示模式和条件改变等排除原因。缺少延迟结果时保留缺失计数，不补成零分。`mergeOutcomeExports()` 用试验 ID 合并备份，拒绝同一记录下互相冲突的答案与身份字段；这保证记录不乱加，但没有核实真实参与者身份。
- **分析路径**：先检查样本来源、去重、流失和分组；若做因果试验，预先定义指标，随机分配条件并控制学习时长，处理延迟测缺失。
- **Trade-off**：严格对照更能回答效果问题，但组织成本高；真实使用数据外部环境更自然，却难识别因果。
- **追问**：多个备份或不同试验 ID，为什么不能直接算多个独立学习者？
- **追问答案**：一个人可以反复导出同一记录，也可能在多个工作区开始新试验。相同试验 ID 能去掉备份副本，不同 ID 却不能证明是不同人；当前项目没有身份核验体系。因此汇总应报告去重后的试验记录数、重复标记和缺失情况，真实研究还需由负责人确认参与者及独立作答条件。

### Q59：当前最重要的生产差距是什么？你会如何排序？

- **口述答案**：先统一 CLI 输入限额差异，并保持已修正的 CI 团队测试竞态回归，再扩大真实质量评测与独立学习者验证，按发布需求补正式发行与平台验收。新厂商、Gemini、SDK/App Server 按需扩展。云化另需多租户身份、队列、配额和隔离，不能把本地程序直接包装成 SaaS。
- **知行具体怎么做**：曾发现 CLI `execute()` 独立的 8,000 字符限制，现已改用共享 20,000 上限并通过真实入口对照；其余工程补强与验证已按 2026-09-18 台账推进，具体完成项和外部验收限制分开列出。CI 等待竞态已由 `485b358` 修正且 #46 通过，应保持回归而非继续列作未定位故障。质量侧仍缺更多独立题和真实学习者；正式分发与新版跨平台实包验收则按实际交付需求补齐。
- **分析路径**：按用户风险、证据缺口、依赖条件和可交付范围排序；先验证价值，再投入不必要的基础设施。
- **Trade-off**：过早做云化和所有厂商增加维护成本；只保持本地模式限制协作与运维能力。选择应服从用户和规模，而非技术清单。
- **追问**：架构允许扩展，能写成已服务百万用户或已经完成全部正式发行吗？
- **追问答案**：不能。扩展接口只能说明可以接入什么，用户规模需要真实运营记录，云化还要实际建设身份、队列、配额与隔离并做负载验证。固定本地签名也不等于正式证书、公证和各平台发行验收。面试应分别列“当前代码”“历史验收”“未完成项”，用可查证据支撑每一句。

### Q60：面试时如何讲清这个项目，同时不夸大自己的贡献？

- **口述答案**：用“用户问题—关键决策—实现责任—失败案例—验证证据—剩余边界”展开。讲自己确实能解释和复现的模块，说明 AI 辅助开发的范围以及自己如何审查、测试和纠正，不把生成代码量当主要贡献。
- **知行具体怎么做**：可以沿真实证据链讲成员预算案例：H02 成员耗尽输出额度，资源策略识别推理与正文共享额度，未手动指定时按可用容量选择档位，并给审查和最终回答保留目标。源码、预算测试和前后记录能对应起来；回归虽然完成，仍有成员初答错误、额外纠正和接近总时限的限制。这种讲法展示决策与证据，不预设个人曾独立完成全部实现。
- **分析路径**：选一个可深入追问的案例，例如成员预算耗尽；展示先前失败、诊断证据、资源策略、定向测试与真实回归，再解释结论为什么有限。
- **Trade-off**：真实边界看起来少一些“成绩”，却更经得住追问；宽泛地说架构对齐顶尖产品很难验证。
- **追问**：“我设计”“我实现”和项目数字应该怎样表述，才不夸大个人贡献？
- **追问答案**：只把自己实际参与、能够解释和复现的部分写成个人职责；与他人或 AI 协作的成果说明任务分工、自己做过的审查、测试或纠错。数字同时注明题目数、运行数、构建和评分口径。无法确认归属时说“项目实现了”，无法复现的性能或准确率不要放入简历。

## 失败原因与实际取舍

1. **内部格式可靠性不足。** 异模型团队四题的 DeepSeek 报告即使自动修正一次仍未满足 schema；这些 API 请求本身均完成，不属于钥匙串、连接或超时。旧记录没有保存被拒绝报告原文，因此不能断言四次都由某个具体字段类型造成。源码确认通用修正提示会重新要求“遵守用户篇幅和格式要求”，与内部核查协议冲突；原问题又作为最近的用户指令进入成员上下文。这是确定存在的实现问题，但其在每次真实失败中的贡献尚不能精确分离。
2. **多次调用扩大执行失败机会。** 本轮三次 Pi 请求失败：单组 Q03 最终回答、异模型 Q03 最终回答、异模型 Q06 审查。异模型两个成员在后两题都完成，后续 Pi 阶段失败仍使整组不完整。需要保留部分结果，不能把中间成功等同于整组成功。
3. **审查不等于证明。** Q04 的解释缺口未被完全消除；Q06 的审查也表明团队可能找出题面缺陷。应评估证据覆盖和问题歧义，而不是只统计一致投票或复核次数。
4. **延迟及用量增加。** 同模型常规流程含分工、两位成员、审查、最终回答；Pi 成员按现有共享通路顺序调用。异模型成员并发，但 Kimi 响应及格式修正、后续串行审查与综合决定总时长。本轮同模型/异模型耗时中位数约为单 Pi 的 4.4/6.9 倍。

普通 Pi 在七个成功请求上全部答对并解释通过，存在明显的样本上限；自检 8/8 相比普通 7/8 的唯一差距是 Q03 请求失败，不能据此证明自检提升了推理质量。相同道理，这八题一次运行不足以得出所有异模型合作方案都更差的结论。旧版 96 任务报告与本轮题集、协议不同，不作百分点增益比较。

## 后续修复与验收边界

本轮结束后才修改内部请求和修正协议：原始用户对话作为任务数据，当前内部指令明确要求对应 JSON；格式修正返回有界字段路径与类型信息，不复制模型原文或未知字段名。仅合成评测增加脱敏 `reportIssue`，以便区分语法、字段与长度问题。旧题 H02/H04 的后续回归、实际包检查与安装状态另行记录，不改写上面的新题成绩。

解释评分由开发助手非盲逐条完成，不是独立人类盲评，更不是学生学前/学后或 72 小时保持效果实验。正式质量优势仍需更多无歧义的新任务、配对重复试验和独立评阅。用户模式选择保持三种；团队不自动替换默认单 Agent。

# GitHub verify #44：团队设置等待竞态

日期：2026-09-11。应用架构基线为 `60570bc`，修复前工作区为文档提交 `d14ee2f`。本次修正 UI 测试及对应状态说明，没有修改团队调度、模型接入或账号配置。

## 原始失败

[verify #44](https://github.com/muzigef/zhixing/actions/runs/34576546164) 的两套生产依赖审计和 `npm run verify` 成功，桌面前六组 UI 成功；团队测试在当时 `smoke-team.mjs:53` 点击“发送消息”超时：`locator.click: Timeout 8000ms exceeded`，按钮为 disabled。

失败快照中同模型团队已正常完成，输入框为空，后台无正在运行的会话。初始日志只显示症状；本次本机重跑原脚本也失败，继续追踪输入与焦点事件后确认了原因。[文档提交的 verify #45](https://github.com/muzigef/zhixing/actions/runs/34587030033) 在未修改脚本的情况下通过，说明此故障受时序影响；该成功没有改变 #44 的失败事实。

## 原因与修复

1. 点击团队设置的“保存团队配置”，`TeamSettingsPanel` 立即把按钮改名为“保存中…”，然后等待实际设置保存及返回。
2. 旧脚本等待名为“保存团队配置”的按钮隐藏。按钮改名就满足这一条件，而原生模态对话框仍打开。
3. 脚本过早对背景输入框执行 `fill()`；模态框阻挡焦点，诊断事件显示第二次填字没有到达聊天 textarea。输入框仍为空，发送按钮正确保持禁用。
4. 改为等待名为“团队配置”的 **dialog 真正隐藏**，再填字并断言实际输入值；原 8 秒超时保持不变。

对应源码：[团队设置](../../desktop/renderer/team-panel.tsx)、[模态对话框](../../desktop/renderer/index.tsx)、[修复后的 UI 测试](../../desktop/scripts/smoke-team.mjs)。这是自动化脚本把“按钮改名”误当成“保存完成”的问题；没有发现该路径上的团队计算或会话数据丢失。

## 可重复的回归场景

测试只在独立临时工作区中，通过 Promise 闸门暂停 `preferences.json` 的读取，主动保持设置请求未返回。确认“保存中…”禁用、原按钮名称已不存在、对话框仍显示，随后释放保存请求并等待对话框关闭。异常路径也释放闸门，避免错误诊断读取设置时卡住。

修复前，在同一闸门场景下，“输入前对话框必须关闭”的断言稳定失败：实际 `true`、预期 `false`；修复后团队全流程通过，保留 25 次合成模型调用、定向补做 3 次调用且不重放同伴、整队重跑、预算保存和停止回归。

所有 HTTP、密钥加解密均为隔离夹具，未使用真实模型或已有用户凭据。闸门没有进入应用代码，不依靠增加等待秒数规避失败。

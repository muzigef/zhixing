# Pi / Codex 延迟分析

> 历史验收快照：下文的测试数量、失败、安装及“待验”状态仅适用于记录当次执行；未重新运行或改写历史结果。当前实现与后续进展见 [当前状态](../current-status.md) 和 [证据索引](README.md)。

日期：2026-09-07。基于 `13b88f0` 的桌面调用链、Pi SDK 0.85.0、`gpt-5.6-terra`。本次完成原因分析、诊断脚本及真实对照；性能修复尚未进入产品代码。

## 结论

知行有明确的优化空间。当前“每轮新建 worker、自动使用 WebSocket、等待进程退出才完成本轮”的组合，使模型已经完成后的连接收尾进入关键路径。18 个 WebSocket 模型轮次的这段等待中位数为 **3.230 秒**。两轮工具任务会承担两次。

另一方面，较慢的工具续答确实出现了连接已建立、服务已报告 `response.in_progress` 后长时间没有内容输出的现象。这部分不能由本地工具、SDK 初始化或前端渲染解释；其内部原因仍可能涉及服务端调度、推理或网络流传输，现有客户端证据不能继续拆分。

此前 42.587 秒的实包请求没有分阶段记录，不能把其全部耗时归因于本次发现的收尾等待，也不能还原它每轮的远端等待。此次同类工具任务出现 13.202–33.617 秒的 WebSocket 总耗时，说明 42.587 秒不宜当作固定调用成本。

## 方法与范围

- 18 个真实合成任务，共 27 轮模型请求，全部完成。六种条件各 3 个样本，串行执行。
- 使用真实 `DesktopService`、`LearningApplication`、`PiApplicationClient` 和构建后的公共 SDK worker；Node v24.8.0。使用临时学习工作区，实际状态为 RAG 尚未开始，无用户资料。
- 文本题固定为“2+2 等于几？只回复一个数字。”；工具题明确要求调用 `learning_progress`，再用一句话回答当前学习日及状态。
- `balanced` 继承 Pi 的 `medium`；`quick` 映射为 `low`。当前的“快速”是推理档位，不是服务优先级切换。
- `auto` 组保留生产 worker。SSE 组只在临时 worker 副本的 SDK 调用参数中增加 `transport: "sse"`，无其他模型参数变更。原 worker 的 SHA-256 保存在原始 JSON 中。
- preload 只记录时间戳、白名单事件名和 HTTP 状态；不记录 URL、请求头、请求内容、网络错误正文或认证数据。Pi 的认证仍由产品公共 SDK 内部处理。
- 本次没有重新运行 Electron 实包 UI、直接 Codex 客户端、DeepSeek 或复杂回答质量对照。每组只有 3 次，顺序固定、未随机化，存在文件缓存预热和远端负载波动，不构成 SLA、P95 或稳定提速保证。

原始证据：[首批 6 个任务](pi-latency-20260907.json)、[重复 12 个任务](pi-latency-repeat-20260907.json)。此前实包结果见 [登录后可用性](pi-availability-20260907.md)。

夹具核对：诊断脚本初稿调用了“开始第 1 天”，但新工作区未满足 RAG 的前置课程，开始操作被课程规则阻止，实际进度始终是“rag：尚未开始”。因此这些样本是未开始状态的工具查询，不能称为 D01 进行中验收。当前脚本改为显式校验这个未开始状态。各对照组的夹具一致，连接事件和耗时记录仍有效；与此前实包 D01 请求不是完全相同的输入状态。少数回答还把主题 ID `rag` 称为“学习日”，这是另一个内容质量问题，不能把协议 completed 等同于答案全部正确。

复现命令（使用已安装的根目录、desktop 依赖和当前构建 worker）：

```bash
node_modules/.bin/tsx scripts/profile-pi-latency.ts --live --output=docs/evidence/pi-latency-20260907.json
node_modules/.bin/tsx scripts/profile-pi-latency.ts --live --repetitions=2 --output=docs/evidence/pi-latency-repeat-20260907.json
```

复现时请为 `--output` 使用新的文件名，保留历史证据。`--cases=text-balanced-auto,text-balanced-sse` 可限制范围；无 `--live` 或设置 `ZHIXING_ALLOW_LIVE_PROVIDER=0` 均拒绝请求。脚本不修改 Pi 设置。

## 实测对照

全部单位为秒。“首字”从生成任务开始计算，只计可见正文；工具事件不计入首字。“完成”还包含进程退出，二者不能相加。

| 条件 | 次数 | 首字中位数 | 完成中位数 | 完成范围 |
| --- | ---: | ---: | ---: | ---: |
| 数字问答 / 均衡 / 当前 auto | 3 | 2.764 | 6.080 | 5.850–6.451 |
| 数字问答 / 快速 / 当前 auto | 3 | 3.277 | 6.637 | 6.247–6.839 |
| 工具续答 / 均衡 / 当前 auto | 3 | 10.800 | 14.362 | 13.202–24.581 |
| 工具续答 / 快速 / 当前 auto | 3 | 9.679 | 14.205 | 12.948–33.617 |
| 数字问答 / 均衡 / SSE 对照 | 3 | 2.292 | 2.850 | 2.547–3.388 |
| 工具续答 / 均衡 / SSE 对照 | 3 | 6.979 | 7.622 | 7.409–18.239 |

SSE 总耗时中位数更小，但也出现 18.239 秒的工具任务；不能声称每次 SSE 都比 WebSocket 快。最稳定的收益证据是下列连接收尾时间差。

| 每轮阶段 | 当前 auto / WebSocket | SSE 对照 |
| --- | ---: | ---: |
| SDK 初始化中位数 | 0.499 | 0.502 |
| WebSocket 握手中位数 | 0.884 | 不适用；HTTP 仅测请求到响应头 |
| worker 发出 done → 进程退出中位数 | **3.230** | **0.350** |
| done → 退出范围 | 3.221–4.232，18 轮 | 0.332–0.365，9 轮 |

18 个 WebSocket 轮次都记录到打开和响应完成，没有记录到 WebSocket 错误或 SSE 回退；本次未发现反复重试导致的延迟。9 次本地工具执行为 0–1 毫秒，0 表示低于本次毫秒计时分辨率。

## 原因一：模型完成之后，仍等待连接关闭

首批数字问答的时间线（相对于 worker 进程启动请求）：

| 时间 | 事件 |
| ---: | --- |
| 0.988 秒 | 开始 WebSocket 连接 |
| 1.872 秒 | 连接打开 |
| 3.120 秒 | 收到正文增量 |
| 3.170 秒 | 收到 `response.completed` |
| 3.171 秒 | SDK 请求关闭 WebSocket |
| 3.172 秒 | worker 已发出 `done` |
| 6.426 秒 | WebSocket 实际关闭 |
| 6.448 秒 | 进程退出，adapter 才允许本轮完成 |

在这次 6.451 秒的回答中，3.276 秒发生在 worker 发出完成事件之后。这部分不是生成数字“4”的时间。

源码关系：

- 历史桌面 worker（已合并到[共享 worker](../../src/pi-model-worker.ts)；以下描述当时实现）使用 `streamSimple`，未指定 transport、sessionId 或完成后的资源生命周期策略。
- [PiApplicationClient](../../src/pi-application-client.ts) 每轮新建进程；只有同时读到协议 done 和成功退出后，才向应用发出 done。
- [runPiProcess](../../src/pi-client.ts) 等待子进程 stdout 结束和 close。
- 安装的 Pi SDK `dist/api/openai-codex-responses.js`：默认 transport 为 auto；未传 sessionId 时 `acquireWebSocket` 创建临时连接，并在 release 时调用 close；`processWebSocketStream` 收尾后才交付 SDK done。其 close 调用不等待握手完成，但未关闭的连接仍使 worker 进程存活。

**确认的是关闭请求到实际关闭的等待，以及应用将它纳入完成条件。** 尚未确认为何当前环境的关闭握手约需 3.2 秒，不将其写成 SDK 中存在固定 3 秒 sleep、账号限制或特定网络故障。

## 原因二：每次工具续答重新初始化并建连

一个进度查询走的是：准备上下文 → 模型产生工具调用 → worker 收尾退出 → 本地工具 → 新 worker 初始化与建连 → 模型生成一句话 → 再次收尾退出。

首批均衡工具任务 14.362 秒可分为：

| 阶段，两轮合计 | 耗时 |
| --- | ---: |
| 进程启动请求 → 开始连接，含 SDK 初始化等准备 | 1.092 秒 |
| WebSocket 握手 | 1.783 秒 |
| 连接打开 → worker done，含远端等待、生成及协议转发 | 4.979 秒 |
| worker done → 进程退出 | **6.494 秒** |
| 本地工具 | 0.001 秒 |
| 上下文及其余应用协调 | 约 0.013 秒 |

[工具循环](../../src/model-invocation.ts) 在完整 Provider 轮次通过协议和预算校验后才执行工具；这是正确性边界。应改进连接生命周期，不应把未验证的工具参数增量直接拿去执行。

SDK 自身已有按 sessionId 复用 WebSocket、连接内 previous_response_id 和增量上下文的实现。知行当前既不传 sessionId，又每轮退出进程，因而不能使用这些连接复用能力。只补一个 sessionId、却继续每轮换进程，也不能复用原连接。

本次全部 cacheReadTokens 为 0。这不证明模型不支持缓存，也不证明未传 sessionId 会关闭所有服务端缓存；只能说明本次没有报告缓存命中。

## 原因三：远端首内容等待有明显长尾

重复测试的一次快速工具任务耗时 33.617 秒。第二轮连接在 1.355 秒打开，服务在 2.114 秒报告 `response.in_progress`，直到 23.269 秒才出现第一个输出项；可见正文在 23.272 秒出现。

这约 21 秒的间隔发生在连接建立和请求开始之后。本地工具已经完成，因此优化 SQLite、React 或 SDK 导入无法消除它。客户端不能进一步判定是服务排队、模型推理还是流传输停顿。原有 `modelMs` 是整个模型/工具循环的墙钟时间，也不能用它直接代表 OpenAI 推理时间。

“快速”在本次三个数字问答中没有更快，工具任务中位数与均衡近似且仍有长尾；小样本不能证明降低推理强度无效，但没有依据将它作为本问题的主要修复。应使用更多交错样本，并把复杂回答质量作为共同验收指标。

## 原因四：进度展示和可观测性使等待更难理解

- worker 当前只转发正文、最终工具调用和 usage，不转发连接/请求接受/工具参数准备等阶段状态。
- 工具活动是在整个 Provider 轮次完成后才开始展示；[界面](../../desktop/renderer/index.tsx) 的活动列表还默认折叠。用户可能长时间只看到“组织回答”。
- 正文虽然已经流式到达，但任务仍可能因连接收尾而保持 running，延迟后续队列任务开始。
- SDK 初始化、连接、模型完成、工具执行、进程退出应分别计时；`reasoningTokens` 未提供时应保留 unknown，不能统一填 0 后推断模型没有思考。

真实阶段反馈可以改善体感，但不会自动缩短远端计算。本次没有采集 React 帧率，因此不将渲染列为已证实的主瓶颈。

## 建议开发顺序

| 优先级 | 改进 | 证据与预期 | 验收重点 |
| --- | --- | --- | --- |
| P0 | 将本次分阶段诊断变为产品内的脱敏计时，按 Provider、transport、轮次统计 | 当前计时无法解释长尾；这是持续优化依据 | 记录未知值；不保存凭据/请求正文；区分首字、模型完成、应用完成 |
| P0 | 给当前短生命周期 Pi worker 增加明确的 SSE 传输策略及回退配置 | 本环境每轮完成后的等待中位数从 3.230 降到 0.350 秒 | 保留整轮协议校验、取消和错误处理；复测实际安装包；复杂工具/长回答质量回归 |
| P1 | 复用仅模型 worker 和 ModelRuntime，并按应用会话传稳定 sessionId | 可避免重复 SDK 初始化、连接握手，使用 SDK 的连接内续答；具体总收益待测 | 每请求有独立编号与完成边界；隔离会话/模型切换，停止和退出可靠清理；工具仍经 ToolHarness |
| P1 | 减少不必要的模型往返 | 进度数据本地可查；明确的进度入口可直接显示卡片，自然语言问题可复用已授权、最新上下文 | 不用僵硬关键词误判开放任务；用户明确要求调用工具时照常执行；不省略必要的事实验证 |
| P1 | 细化可见阶段，及早展示真实工具准备/执行状态 | 长尾期间用户能知道任务仍在进行；完成状态不再被连接收尾拖住 | 展示简短状态，不暴露内部思考；不能提前宣称工具已执行 |
| P2 | 按任务选择推理档位、按需检索/加载工具，保持稳定上下文前缀 | 当前授权主题每次先 overview/search，工具集合较宽；对更长会话值得优化 | 保留复杂教学质量、权限边界及跨主题隔离；用成功率、首字与总耗时共同评估 |
| P2 | 长回答增量渲染与独立只读工具的有界并行 | 当前每段正文触发 Markdown 更新，工具批次串行；属于后续扩展优化 | 先做渲染/真实慢工具剖析；不可并行有依赖或有写入顺序的操作；本次单个 1ms 工具不会获益 |
| P2 | 进度工具返回具名字段，如 topicId、activeDay、state | 当前工具返回简短字符串，部分样本把 rag 主题 ID 当作学习日 | 验证未开始、进行中和前置课程阻塞三种状态；协议成功与内容正确性分别统计 |

当前上下文与本地进度工具开销很小，优先级低于连接管理。也不应仅因代码写了 `maxTokens: 16384` 就认定模型在生成大量内容：这些测试只生成少量 token，且安装的 Codex SDK `buildRequestBody` 没有把该参数写成 `max_output_tokens`。调整输出上限前须核对实际 Provider 参数支持，不能将配置字段变化当作性能收益。

OpenAI 官方延迟指南同样建议减少串行请求、展示真实进度，并对确定性结果使用传统程序/UI；这些是架构原则，不是本订阅通道的性能承诺。[OpenAI Docs：Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)

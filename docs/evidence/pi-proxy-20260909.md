## 已观察到的现象

- 终端进程没有设置大小写 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 环境变量。仅检查变量是否存在，没有输出潜在的认证信息。
- 本机 `127.0.0.1:15236` 存在监听，所属应用为 Veee。
- 对 ChatGPT 公共站点直连，5 秒超时，curl 退出 28；显式 HTTP 代理可完成 CONNECT 和 TLS，总耗时约 2.92 秒，站点返回 403。这只证明网络通路，不能证明订阅模型可用。
- 使用已安装 Electron 的 Node 24.20.0，以 `ELECTRON_RUN_AS_NODE=1`、`NODE_USE_ENV_PROXY=1` 和上述 HTTP(S) 代理环境进行无凭据 fetch，1123 ms 返回同一站点的 HTTP 403。
- 在没有代理环境的完整十二行开发题运行中，所有 Pi 请求失败，约 11.3 秒结束；DeepSeek 和 Kimi 能返回。保留[原始运行](team-evaluation-pilot-20260909123534727.json)，不将连接失败描述为模型解题错误。
- 同一包继承上述代理变量后，首个真实 Pi 请求成功，根任务 7296 ms，答案通过冻结评分器；随后自检和同模型团队均完整成功。这比公共站点连通检查更直接地确认了订阅通路可用。

可复现的启动环境及后续完整质量结果见[冻结协议补记](../agent-team-evaluation-protocol-20260909.md)和[质量对照报告](team-quality-comparison-20260909.md)。直连与代理的先后对照支持“当前 Pi 失败与代理环境缺失有关”，并不排除其他时间段上游网络波动。

## 权限问题的区别

用户截图中已开启录屏的是 ChatGPT 主应用；电脑操作另有 `ChatGPT Computer Use` 辅助应用，需在系统录屏列表单独启用。用户完成后，本次 CUA 已能实际读取知行窗口并操作设置。[OpenAI Computer Use 文档](https://learn.chatgpt.com/docs/computer-use)说明操作系统录屏/辅助功能权限与应用访问许可属于不同层次。

使用知行设置内的 Kimi“测试连接”，界面实际显示“连接正常 · 首字 25.9 秒 · 总耗时 25.9 秒”；随后真实评测中 Kimi/DeepSeek 也完成请求。本轮受控凭据访问已通过，不能继续把留出评测标为等待用户授权。

另经只读签名检查，知行 0.9.2 与 0.10.0 预览包均为 ad-hoc 签名，指定要求分别依赖不同的代码哈希。这能够解释重打包后系统将其视为新代码身份并可能再次请求 Keychain 授权。[Electron safeStorage 文档](https://www.electronjs.org/docs/latest/api/safe-storage)要求稳定、有效签名以保持凭据访问；[Apple 签名说明](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)解释 Keychain 的指定要求匹配。不能仅凭之前出现 SecurityAgent 或准备阶段等待，就断言用户没有点击“始终允许”；历史等待记录保留，但具体弹窗原因并未逐次认证。

本次没有更改系统权限策略或交付稳定签名方案。代理环境仅用于启动评测及其子进程，Finder 正常启动不保证继承；持久应用代理配置也未在本次连通性验证中实现。

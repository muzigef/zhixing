## 覆盖范围

- 输入路径穿越、大小写/保留名/文件与目录冲突，输入字节预算；不支持的能力在启动前拒绝。
- 外部合成文件读取/改写、符号链接逃逸、TCP 与 POSIX Unix socket；带目录读取授权仍不能通过 socket 发起通信。
- Node 和 Python 两种真实运行时；子进程拒绝与工作目录正常读写；MCP restricted 走相同入口。
- 墙钟、CPU、内存、工作目录文件/字节预算、输出洪泛，以及正在执行时取消和临时目录清理。
- stdout 伪造成功不能改变可信退出回执；资源超限有独立状态及原因，测试失败不能保存为已通过的检查点。
- AST 扫描全部应用源码入口，禁止绕过网关/后端登记；旧 Codex 真实执行旁路已关闭。

## 修复与失败历史

保留失败 run，避免把首轮失败说成一次通过：

1. [首轮](https://github.com/muzigef/zhixing/actions/runs/35200407032)：Mac 两架构通过；Linux GCC 拒绝忽略 read/write 返回值；Windows 综合探针需要使用继承 stdio，并补下载 Electron 二进制。Windows 内存/CPU/目录/输出与取消探针当时已通过。
2. [第二轮](https://github.com/muzigef/zhixing/actions/runs/35200934593)：Windows 与 Mac 通过；Linux 不支持错误使用的 `--preserve-fds` 参数。按 bubblewrap 官方源码确认 FD 继承规则后修正，没有降级执行。
3. [第三轮](https://github.com/muzigef/zhixing/actions/runs/35201403321)：Linux MCP 探针发现私有挂载中工作目录外仍可写；这是违反工作目录策略及配额覆盖的问题，并不证明宿主文件已被改写。随后只读重挂载 root/tmp/dev，另以 seccomp 拒绝 socket/connect 并增加 Unix socket 实测。
4. [第四轮](https://github.com/muzigef/zhixing/actions/runs/35201630445)：上述问题修复后，四个平台均通过。

本地首轮完整门禁只在最终 diff 检查发现一处文件尾空行，已修复。临时验证 worktree 曾被 Vitest 重复收集，已将生成目录 `.build/` 排除；最终只计算真实源码目录中的 157 个测试文件，没有跳过失败用例。

## 能力限制与未执行项

- macOS/Linux 内存是 RSS 监控终止，不是瞬时硬上限；Windows Job Object 限制提交内存，统计口径不同。要求硬内存限制时，不满足的后端拒绝启动。
- 目录配额采用监控，不能保证宿主瞬时磁盘/内存占用不超额，不作为多租户敌对代码托管服务的保证。
- Windows 交互式 restricted MCP / 外部读目录授权尚不支持，统一入口明确拒绝；没有转为 trusted。
- trusted MCP、固定认证/模型进程、OCR 解析器仍有各自的宿主信任边界；入口登记不等于 OS 隔离。
- 本轮没有真实模型质量/教学效果评测、钥匙串凭据访问、正式签名公证或安装包替换；这些不属于本次沙箱边界验收。
